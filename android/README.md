# Repas : l'application Android

L'application Android de Repas (tickets `DRV-311` à `DRV-319`, dépôt back `docs/drive/`) : **l'application Repas complète**. Une **coquille** ([`MainActivity`](#la-coquille-repas-drv-317)) charge le front Repas dans une WebView ; le drive Leclerc est un **second écran** (`DriveActivity`, WebView en mode ordinateur où l'agent de `drive-agent/` est injecté) que la coquille ouvre. Repas parle à l'application par le **pont natif** `window.repasNative`. **Écrite en Kotlin, AndroidX réduit au strict nécessaire.**

État : **coquille Repas** (DRV-317), **hôte WebView du drive** (DRV-312, devenu `DriveActivity`) et **agent embarqué** (DRV-313). **Passage du plan et retour du résultat** (DRV-314) : `drive.start` ouvre le drive sur le magasin du plan, l'agent s'exécute, `drive.result` revient à Repas. **Lecture du magasin** (DRV-320) : `drive.setup` ouvre le drive pour que l'utilisateur choisisse son magasin, que l'agent lit. **Essais complets dans l'émulateur** (DRV-319) : `make android-e2e` joue de vrais passages (l'agent réel, la vraie WebView) contre le faux site Leclerc complet. **Publication signée** (DRV-315) : une étiquette `android-vX.Y.Z` poussée par l'humain lance [`android-release.yml`](../.github/workflows/android-release.yml), qui construit, contrôle et publie l'APK signé de sa clé (procédure pas à pas, étapes humaines comprises : [`PUBLICATION.md`](PUBLICATION.md)). Le nom de paquet reste `eu.kantin.repas.drive` (il ne change plus : un paquet renommé ne se met pas à jour par-dessus l'ancien).

> Ce dossier prolonge l'application de test jetable du spike (DRV-011, `drive-agent/android-lab/`) et le banc d'essai du favori (`drive-agent/lab/`), **retirés le 2026-10-19** (ils restent dans l'historique Git).

## Commandes

Tout se lance dans Docker (image : JDK 17, Gradle, SDK Android ; rien à installer sur la machine). La première construction télécharge les outils, les suivantes réutilisent le cache.

| Commande | Rôle |
|---|---|
| `make android-agent-hash` | note l'empreinte SHA-384 de l'agent construit dans `android/agent.js.sha384` (après un changement voulu de l'agent) |
| `make android` | construit l'APK de débogage : `android/dist/repas-drive-debug.apk`, avec sa taille et son empreinte SHA-256 |
| `make android-test` | joue les tests Kotlin : ceux de l'application et ceux de la dérivation de la version (`buildSrc`) |
| `make android-release` | construit l'APK signé `android/dist/repas-drive.apk` ; **refuse sans clé de signature** ni étiquette de version (`ANDROID_VERSION_TAG=android-vX.Y.Z`, dont le code de version est tiré) |
| `make android-release-verify` | contrôle l'APK signé juste après sa construction (`ANDROID_VERSION_TAG` et `ANDROID_EXPECTED_CERT_SHA256`, l'empreinte SHA-256 publique attendue du certificat) : signature et certificat, version, une seule permission, non débogable, `BuildConfig.DEBUG` faux, agent intact ; écrit `dist/release-facts.env` |
| `make android-release-selftest` | prouve le refus sans clé, la réussite avec une clé jetable créée à l'instant et les refus du contrôle (mauvais certificat, autre version, clé de débogage) ; rien n'est conservé |
| `make android-emulator-up` | démarre l'émulateur de test et attend la fin de son démarrage (voir « Émulateur de test » plus bas ; demande KVM) |
| `make android-emulator-down` | arrête l'émulateur (le SDK et l'AVD restent dans leur volume) |
| `make android-emulator-status` | dit si KVM, le volume du SDK et l'émulateur sont prêts (code 0 seulement s'il a démarré) |
| `make android-smoke` | test de fumée : construit un APK de débogage qui vise le faux Repas local, démarre l'émulateur au besoin, joue la coquille et le drive sur les faux sites locaux ; rapport et captures dans `android/dist/smoke/` |
| `make android-e2e` | scénarios complets : même APK, contre le **faux site Leclerc complet** (HTTPS) : lecture du magasin, passage complet (phases A et B, retour dans Repas), « Annuler », abandon, application tuée puis reprise, blocage simulé, site changé ; rapport et captures dans `android/dist/e2e/` (voir « Les scénarios complets » plus bas) |

Chaque commande Android reconstruit d'abord l'agent (`make agent-build`, Node dans Docker) : `agent.js` est un actif de l'APK (voir plus bas). La CI le construit avec `setup-node` puis passe `ANDROID_AGENT=` aux commandes `make` pour ne pas relancer Node dans Docker. La CI (`.github/workflows/android.yml`, séparée de `make check`) joue `make android-test`, `make android` et `make android-release-selftest` (donc aussi le contrôle de l'APK signé, avec une clé jetable) ; l'APK de débogage est déposé en artefact du run. Elle ne tourne que si `android/`, l'agent (`drive-agent/src`, `protocol`, `scripts`, `package*.json`), son workflow, `compose.yaml` ou le `Makefile` changent. Lancé à la main sur `main` (`gh workflow run android.yml --ref main`, avec au besoin `-f tag=android-dev-2026-10-18b` pour choisir l'étiquette), il publie aussi l'APK de débogage en **pré-version GitHub** `android-dev-<date>` (jamais une release de production ; mode d'emploi : `PROCEDURE.md`). L'image de construction est mise en cache par GitHub Actions. **La pré-version `android-dev-…` porte un avertissement dans ses notes : signée d'une clé de débogage publique, elle ne s'installe jamais sur le téléphone des courses.**

### La publication signée (DRV-315)

`.github/workflows/android-release.yml` ne se déclenche **que** sur le push d'une étiquette `android-vX.Y.Z` (jamais sur une PR, sur `main` ou à la main) et n'a aucune variante qui publie sans clé. Deux travaux :

1. **`build`** (lecture seule du dépôt, c'est le seul qui voit les quatre secrets, dans l'environnement de deux étapes) : refuse tout de suite, avant de construire, si un secret manque (message qui renvoie vers `PUBLICATION.md`, jamais une valeur) ; vérifie l'étiquette (forme, commit dans `main`, plus récente que les précédentes, pas déjà de release) et l'empreinte du certificat attendu (celle de `public/.well-known/assetlinks.json`) ; construit l'agent et compare son SHA-384 à `agent.js.sha384` ; joue les tests Kotlin ; construit l'APK (`make android-release`, version et code tirés de l'étiquette) ; le contrôle (`make android-release-verify`) ; prépare `repas-drive.apk`, `repas-drive.apk.sha256`, `version.json` (`versionName`, `versionCode`, `apkUrl`, `sha256`, `minAndroid`) et les notes (SHA-256 de l'APK, version et SHA-384 de l'agent, empreinte du certificat, commit, installation en une ligne, rappel sur les pré-versions).
2. **`publish`** (écriture, aucun secret) : vérifie que le fichier reçu a l'empreinte annoncée, crée la release (**ni brouillon ni pré-version**, `--latest=false` pour ne pas prendre l'étiquette « Latest » aux versions du site), puis relit ce qui est publié (empreinte de l'APK téléchargé).

`release.yml` (le site) ignore toute release dont l'étiquette commence par `android-`. `__tests__/publication.spec.ts` garde ces règles (déclencheur unique, droits, secrets seulement dans des blocs `env`, aucun écho) et la forme d'`assetlinks.json` quand il existe ; le contrôle de l'APK est joué par `make android-release-selftest`. **Essayer la construction de publication se fait en local, avec une clé jetable** : `make android-release-selftest` (clé créée à l'instant), ou `ANDROID_KEYSTORE_BASE64=… ANDROID_KEYSTORE_PASSWORD=… ANDROID_KEY_ALIAS=… ANDROID_KEY_PASSWORD=… ANDROID_VERSION_TAG=android-v0.1.0 make android-release` puis `ANDROID_VERSION_TAG=android-v0.1.0 ANDROID_EXPECTED_CERT_SHA256=<empreinte de la clé jetable> make android-release-verify`, et `adb install` dans l'émulateur (`make android-emulator-up`). Une étiquette `android-v…` n'est jamais créée par un agent, ni une vraie clé touchée.

## Émulateur de test (DRV-319)

Un émulateur Android tourne dans Docker, sans fenêtre, pour essayer l'APK de débogage sans téléphone. **Il ne contacte jamais le vrai site Leclerc** : le DNS de l'émulateur envoie tout `*.leclercdrive.fr` vers des faux sites locaux (une page de test, et le faux magasin Leclerc complet de `drive-agent/fake-leclerc/`, sans aucune donnée d'enseigne) et ne résout aucun autre nom. Seul le premier lancement va sur Internet, pour télécharger le SDK chez Google (`dl.google.com`).

Cibles manuelles : la CI n'a pas KVM, elle ne lance jamais l'émulateur, et `make check` n'y touche pas.

### 1. Activer KVM (étape humaine)

L'émulateur a besoin de l'accélération matérielle, sinon il est inutilisable. Sous WSL2, `/dev/kvm` n'existe pas tant que le module n'est pas chargé. Vérifier : `ls -l /dev/kvm` (une ligne `crw-rw-rw-`).

- **À la main** (à refaire après chaque redémarrage de WSL) : `sudo modprobe kvm_intel && sudo chmod 666 /dev/kvm` (processeur AMD : `kvm_amd`).
- **De façon permanente** : dans WSL, `sudo nano /etc/wsl.conf` et ajouter (sans écraser une section `[boot]` qui existerait déjà : dans ce cas, ajouter cette commande à la ligne `command` existante avec `&&`) :

  ```ini
  [boot]
  command = modprobe kvm_intel && chmod 666 /dev/kvm
  ```

  Puis, côté Windows (PowerShell) : `wsl --shutdown`, et rouvrir WSL. Les commandes `make` ci-dessous refusent de démarrer sans KVM et rappellent cette étape.

### 2. Lancer, arrêter, vérifier

| Commande | Effet |
|---|---|
| `make android-emulator-up` | démarre l'émulateur (Android 14, Google APIs, x86_64) et attend `sys.boot_completed` |
| `make android-emulator-status` | KVM, volume, état de l'émulateur |
| `make android-smoke` | le test de fumée (ci-dessous) |
| `make android-e2e` | les scénarios complets contre le faux Leclerc (ci-dessous) |
| `make android-emulator-down` | arrête l'émulateur |

- **Premier lancement** : télécharge environ 2 Go (outils, émulateur, image système ; 6 Go sur le disque une fois décompressé) dans le volume Docker `repas-front_android-emulator-sdk`, crée l'AVD `repas`, puis démarre : 2 minutes 45 mesurées avec une bonne connexion. **Ensuite** : une trentaine de secondes, rien n'est retéléchargé. Pour repartir de zéro : `make android-emulator-down` puis `docker volume rm repas-front_android-emulator-sdk`.
- **Dans l'émulateur** : `docker compose --profile android-emulator exec android-emulator adb <commande>` (par exemple `adb logcat -d`, `adb shell`). Aucun port n'est publié sur la machine.
- Réglages : `EMULATOR_MEMORY` (Mo, 3072 par défaut) et `EMULATOR_CORES` (4 par défaut), par exemple `EMULATOR_MEMORY=4096 make android-emulator-up`.
- **Écran : celui d'un Pixel 9** (le téléphone de l'utilisateur), 1080 × 2424 pixels à 420 dpi, soit 411 × 923 dp (`EMULATOR_LCD_WIDTH`, `EMULATOR_LCD_HEIGHT`, `EMULATOR_LCD_DENSITY` pour en changer). Réécrit à chaque démarrage : un AVD créé avant ce réglage (720 × 1560 à 320 dpi) le reçoit au prochain `make android-emulator-down` puis `up`. Un écran plus petit ou plus grand cacherait le défaut de lisibilité du site en mode ordinateur (voir « La lisibilité en mode ordinateur »). Les captures sont de 1080 × 2424.

### 3. Le test de fumée (`make android-smoke`)

Environ quatre à cinq minutes une fois l'émulateur démarré (283 s mesurées, dont jusqu'à deux minutes pour le test automatique de l'agent). Il construit l'APK de débogage avec `ANDROID_REPAS_ORIGIN=https://repas.test/` (nom du faux Repas, dans `dist/repas-drive-smoke.apk` : l'APK de débogage ordinaire `dist/repas-drive-debug.apk` n'est pas touché) puis contrôle, dans l'ordre, et écrit le tout dans `android/dist/smoke/rapport.txt` avec des captures (`01-coquille-repas.png`, `02-menu-repas.png`, `03-passage-agent.png`, `04-passage-resultat.png`, `05-abandon.png`, `06-reprise.png`, `07-drive.png`, `08-menu-drive.png`, `09-diagnostic-agent.png`, `10-rapport-selftest.png`, `11-retour-coquille.png`, et pour la lecture du magasin `12-lecture-magasin-accueil.png`, `13-lecture-magasin-confirmation.png`, `14-lecture-magasin-resultat.png`, `15-lecture-magasin-abandon.png`) :

1. le réseau : `www.leclercdrive.fr` et `repas.test` se résolvent vers la machine locale (`10.0.2.2`) et un autre nom ne se résout pas ; sinon le test s'arrête avant d'ouvrir quoi que ce soit ;
2. l'APK de débogage s'installe, l'application démarre sans plantage ;
3. la coquille charge le **faux Repas** (`emulator/repaspage.html`, servi comme un SPA sous `repas.test`) : celui-ci relève qu'il est dans la page principale, que le pont `repasNative` existe, que le cookie est accepté, que l'agent utilisateur est celui d'un téléphone, et qu'`app.info` a reçu sa réponse (`drive: true`) ; un message illisible reçoit `INVALID_MESSAGE`, un type inconnu `UNKNOWN_TYPE` ;
4. `app.menu` ouvre le menu de l'application ; un lien vers un autre site ne s'ouvre pas dans la coquille (navigateur du téléphone) ;
5. **passage du plan**, avec le faux Repas qui envoie `drive.start` : (a) le drive s'ouvre sur l'accueil de l'enseigne (`www.leclercdrive.fr`, la page de départ d'un plan, ici la page locale de test ; jamais `/magasin-123456-123456/`, page 404 du vrai site) avec le message « Ouvre ton magasin… », l'agent ne reçoit rien tant que l'utilisateur n'a pas touché « Choisir mon magasin de test » ; le plan arrive alors à l'agent par le pont une fois la page chargée, l'écran reste allumé, l'agent monte son interface (la vraie : « Prêt à remplir ton panier ») ; « Annuler » puis « Retourner dans Repas » dans cette interface font revenir à la coquille, qui reçoit `drive.result` (même `runId`, issue `aborted`) ; l'écran n'est plus maintenu allumé ; (b) le retour au bout de l'historique demande d'abandonner l'envoi, « Abandonner » donne un `drive.result` `aborted` (code `CANCELLED`) ; (c) un passage interrompu (la coquille revient devant) propose « Reprendre » ou « Abandonner », un second plan reçoit `BUSY` avec le `runId` en cours, « Reprendre » rouvre le drive et renvoie le plan, `drive.cancel` donne un `aborted` et fait disparaître la proposition, un second `drive.cancel` reçoit `NO_PASS` ; (d) l'application tuée en plein passage (`force-stop`) propose la reprise au redémarrage, et le résultat `aborted` choisi est livré à la page de Repas rechargée ;
5 bis. **lecture du magasin** (DRV-320), avec le faux Repas qui envoie `drive.setup` : le drive s'ouvre sur l'accueil du faux site avec le message en français simple (se connecter, choisir son magasin), l'écran reste allumé, et **rien n'est envoyé à l'agent tant que la page n'est pas celle d'un magasin** ; le lien « Choisir mon magasin de test » mène à une page `/magasin-123456-123456-Ville-Test/…` : l'agent reçoit alors `setup`, demande « Enregistrer ce magasin dans Repas ? », « Enregistrer » fait revenir à la coquille qui reçoit `drive.result` (un `setup-result` avec l'identifiant et l'hôte du faux magasin, du même `runId`) ; le retour demande « Abandonner la lecture du magasin ? » et « Abandonner » donne un `aborted` sans magasin ; une lecture pendant un passage reçoit `BUSY`, un `drive.setup` sans `runId` valide `INVALID_SETUP` ;
6. le menu « Ouvrir le drive Leclerc » ouvre `DriveActivity` sur le faux site Leclerc, où le pont `repasHost` et son marqueur de débogage sont en place (le script d'injection a tourné), en mode ordinateur ; ; « Agrandir la page » et « Réduire la page » du menu du drive agrandissent puis réduisent la page de Leclerc (l'échelle de la page lue dans la WebView change de plus de 30 %, capture `07b-drive-agrandi.png`) ;
7. « Diagnostic de l'agent » : la commande traverse le pont jusqu'à la page, et l'agent injecté y monte son interface ;
8. « Test automatique (débogage) » : l'aller-retour complet application, pont, agent, pont, application, jusqu'à l'écran « Rapport du test automatique ». **Le verdict de ce rapport est « KO » avec `Arrêt : UNSUPPORTED_PAGE`, et c'est le résultat attendu** : la page de test n'est pas une page de magasin du drive ; ce qui compte, c'est que le rapport arrive ;
9. le retour ramène à la coquille, dont la page répond encore (`app.info`) ;
10. le bilan : l'application tourne toujours, aucun plantage ni blocage dans le journal d'Android, et le journal du DNS prouve qu'aucune demande n'est partie vers Internet.

Le faux Repas obéit aux ordres que le test dépose sur `/__command` du faux site (`drive.start`, `drive.setup`, `drive.cancel`, `app.info`, `app.menu`, ou un message brut) : aucun toucher dans la page n'est nécessaire, et la page relève chaque réponse de l'application sur `/__report`. **Après un changement dans `android/emulator/`, `make android-emulator-down` puis `make android-emulator-up`** reconstruit le conteneur (le test s'arrête avec ce conseil si `repas.test` ne se résout pas).

Code de sortie : 0 si tout passe, 1 sinon (le détail est dans le rapport et `journal-android.txt`), 3 si KVM manque.

### 4. Les scénarios complets (`make android-e2e`, DRV-319 partie 2)

Là où le test de fumée essaie la coquille et le pont sur une page de test, `make android-e2e` joue de **vrais passages** : **l'agent réel dans la vraie WebView du drive**, contre le **faux site Leclerc complet** de DRV-309 (`drive-agent/fake-leclerc/` : 31 produits inventés, recherche, panier en quantités absolues, ruptures, promotions, défauts simulés, requêtes vérifiées à la lettre, cadence jugée), servi en **HTTPS** sous `courses-test.leclercdrive.fr` ; le faux Repas (`repaspage.html`) joue le front. **Le faux site est fidèle au vrai sur les pages de départ** (recette réelle du 2026-10-18) : la racine de l'hôte du magasin (`https://courses-test.leclercdrive.fr/`) et `/magasin-000001-000001/` (sans ville) y sont des pages **404**, et c'est l'**accueil de l'enseigne** (`https://www.leclercdrive.fr/`, la page de départ d'un plan comme de la lecture du magasin) qui affiche l'accueil du magasin et son bouton « Commencer mes courses », lequel mène à la page du magasin avec sa ville. Pendant ces scénarios, `www.leclercdrive.fr` est relayé vers le faux Leclerc complet (mode « fake » de `testsite.py`, `POST /__www` ; `e2e.sh` le met et le remet en « test », la page locale du test de fumée, en sortant) ; avant de jouer, le script vérifie ces deux faits et s'arrête sinon. Même APK de débogage que le test de fumée (`dist/repas-drive-smoke.apk`, qui vise `https://repas.test/`), même émulateur. Durée : environ **5 minutes** de scénarios une fois l'émulateur démarré (21 s à froid, le SDK étant déjà dans son volume), soit **6 minutes** de bout en bout avec la construction de l'APK (en cache). Rapport texte et captures (`e01-….png` à `e20-….png`, **à lire avant de conclure** : un « OK » sans avoir regardé les images ne prouve rien) dans `android/dist/e2e/`. Code de sortie : 0 si tout passe, 1 sinon (détail dans `rapport.txt` et `journal-android.txt`), 3 si KVM manque.

Chaque scénario repart d'un faux Leclerc remis à neuf (`POST /__fake/reset` : panier vide, journal, cadence et défauts à zéro). Le faux Repas reçoit ses ordres de `/__command` (le plan complet y tient : `android/emulator/e2e/plan-complet.json` et `plan-connu.json`, avec `__RUN_ID__`) et relève chaque réponse de l'application, dont le détail des lignes du résultat (`ingrédient:issue:référence:quantité`).

**Ce que ces essais ne prouvent pas** : DataDome (l'anti-robot), la connexion à un vrai compte, le vrai site, le vrai téléphone : c'est la recette de l'utilisateur (DRV-505). **Constat de la recette réelle (2026-10-18, Pixel 9)** : l'hypothèse de DRV-319 (« la racine de l'hôte mène à l'accueil du magasin », le faux site la redirigeait) était fausse dans sa forme, et sa correction (ouvrir `/magasin-<id>-<id>/`, PR #125) aussi : cette adresse est une **page 404** du vrai site (« la page demandée n'a pas pu être trouvée »). La PR #128 est revenue à la racine de l'hôte du magasin (`https://<hôte>/`), que le faux site servait à tort comme un accueil : **c'est aussi une page 404 du vrai site** (constat de l'application 0.1.3, même texte), et le faux site, qui la servait, a masqué le défaut. C'est la racine de l'**enseigne**, `https://www.leclercdrive.fr/` (`NavigationPolicy.START_URL`, ce qu'ouvre « Ouvrir le drive Leclerc » du menu), qui, session ouverte, affiche l'accueil du magasin de l'utilisateur (son nom, « Je peux retirer ma commande », bouton « Commencer mes courses »), et ce bouton mène aux vraies pages du magasin (`https://<hôte>/magasin-<id>-<id>-<Ville>/…`), où `isStorePage` est vrai. L'application ouvre donc **l'accueil de l'enseigne** pour un plan (`DrivePlan.startUrl`, comme `SetupRequest.startUrl`) et c'est **l'utilisateur** qui touche « Commencer mes courses » ; le faux site reproduit cela (racine de l'hôte du magasin et `/magasin-N-N/` sans ville = 404, accueil sur `www.leclercdrive.fr`) et le scénario 2 échoue si le départ retombe sur la racine de l'hôte du magasin. Le plan part vers l'agent dès qu'une page de magasin est atteinte (ticket E de l'audit `hypotheses-site-reel.md` du dépôt back : voir « Le repli quand la page du magasin n'est pas celle attendue »). **À confirmer sur le vrai site** : le statut HTTP de ces pages 404 (le repli ne se déclenche que sur un vrai statut 4xx, pas sur une page « 404 » servie avec le statut 200, que l'application ne lit pas) et l'adresse réelle du magasin, avec sa ville, qui pourrait s'ouvrir directement (ticket F : la mémoriser à la lecture du magasin).

**Le faux certificat n'est jamais accepté par l'application.** La coquille et le drive refusent un certificat en cause (`onReceivedSslError` annule), l'application n'a ni `network_security_config` ni gestionnaire de confiance : l'APK de publication ne fait confiance à aucun faux certificat. C'est la WebView de l'**émulateur de test** qui reçoit, de l'extérieur (`install_apk` de `lib.sh` écrit `/data/local/tmp/webview-command-line` avec `--ignore-certificate-errors-spki-list=` et l'empreinte de la clé publique du faux site, et d'elle seule), l'ordre de lui faire confiance. `__tests__/emulator-e2e.spec.ts` (joué par `make check`) vérifie que l'application n'écrit jamais ce réglage ni un gestionnaire de confiance, que les plans des scénarios sont de vrais plans du protocole v1 aux produits du faux catalogue, et que les scripts sont de la syntaxe bash valide.

### 5. Comment ça marche

Le conteneur (`android/emulator/`, service `android-emulator` de `compose.yaml`, profil à part pour que `make stop` ne l'arrête pas) lance, dans l'ordre : `dnsmasq` (le DNS, seule réponse : `*.leclercdrive.fr` vers `10.0.2.2`, l'adresse de la machine hôte vue par l'émulateur) ; `testsite.py` (le faux site, HTTPS sur le port 443 du conteneur, avec un certificat jetable créé dans le volume, jamais dans le dépôt) ; l'émulateur (`-no-window -no-audio -gpu swiftshader_indirect`, KVM). Pour que la WebView accepte ce certificat sans toucher à l'application, le test de fumée écrit dans l'émulateur `/data/local/tmp/webview-command-line` avec `--ignore-certificate-errors-spki-list=<empreinte de la clé du faux site>` : seule cette clé est acceptée. Cela ne marche que sur une image Google APIs « userdebug » (pas une image avec Play Store), c'est pourquoi c'est celle-là. L'application n'est pas modifiée : l'APK testé est celui que produit `make android`. Pour `make android-e2e`, le conteneur embarque aussi **Node** (le même que celui du front, copié de l'image `node:24`) qui exécute le **faux Leclerc complet** (`drive-agent/fake-leclerc/`, monté en lecture seule sur `/opt/fake-leclerc`, HTTP sur `127.0.0.1:8099` dans le conteneur) ; `testsite.py` le relaie en HTTPS pour le seul nom `courses-test.leclercdrive.fr` (le reste de `*.leclercdrive.fr` garde la page de test du test de fumée). Son pilotage `/__fake/*` (état, panier, défauts, remise à neuf) n'est offert qu'aux noms de la boucle locale : les scripts y accèdent par `docker compose exec`, jamais l'émulateur.

### 6. Dépannage

- **`/dev/kvm` manque** (message « KVM absent ») : voir 1. Après un redémarrage de WSL, refaire `sudo modprobe kvm_intel && sudo chmod 666 /dev/kvm`, ou rendre cela permanent.
- **`/dev/kvm` existe mais l'accès est refusé** : `sudo chmod 666 /dev/kvm`.
- **Le démarrage dépasse 30 minutes ou le conteneur s'arrête** : les dernières lignes du journal sont affichées ; en entier : `docker compose --profile android-emulator logs android-emulator`. Un téléchargement interrompu se reprend en relançant `make android-emulator-up`. Si le volume est abîmé : voir « repartir de zéro » en 2.
- **Mémoire** : l'émulateur prend environ 3 Go ; si WSL est à court, baisser `EMULATOR_MEMORY` (par exemple 2048) ou augmenter `memory=` dans `C:\Users\<toi>\.wslconfig`, puis `wsl --shutdown`.
- **`make android-e2e` s'arrête sur « le faux site Leclerc complet ne répond pas »** (ou « courses-test.leclercdrive.fr ne se résout pas ») : le conteneur date d'avant Node et du dossier monté ; `make android-emulator-down` puis `make android-emulator-up` le reconstruit (quelques dizaines de secondes, le SDK reste dans son volume). Le journal du faux site : `docker compose --profile android-emulator exec android-emulator cat /sdk/site/fake-leclerc.log`.
- **Un scénario de `android-e2e` échoue sur un texte de l'agent** : les textes cherchés sont ceux de `drive-agent/src/ui/strings.ts` ; si l'agent les change, les adapter dans `e2e.sh` (les captures montrent l'écran réel).
- **« l'émulateur n'est pas prêt » ou « APK manque »** pendant `smoke.sh` lancé à la main : passer par `make android-smoke`, qui construit l'APK et démarre l'émulateur avant.
- **Le test de fumée échoue sur « la page locale ne s'est pas chargée »** : l'émulateur vient peut-être juste de démarrer ; relancer. Voir aussi `docker compose --profile android-emulator exec android-emulator tail /sdk/site/access.log` (les chemins demandés au faux site).

## La coquille Repas (DRV-317)

`MainActivity` charge le front Repas dans une WebView, sur **`BuildConfig.REPAS_ORIGIN`** : `https://kantin.eu/` dans l'APK de publication, toujours. L'APK de débogage peut viser un autre hôte `https` (sans port ni chemin) : `ANDROID_REPAS_ORIGIN=https://hote.exemple/ make android` (le test de fumée vise ainsi `https://repas.test/`) ; un autre nom de fichier se choisit par `ANDROID_APK_NAME`. Hôte, filtre d'intention et pont suivent l'origine ; jamais elle ne vient d'un message ni d'une page.

- **Navigation** (`ShellNavigation`) : seules les pages `https` de l'origine de Repas restent dans la WebView ; toute autre page web (`*.leclercdrive.fr` compris, le drive a son écran) s'ouvre dans le navigateur du téléphone ; les autres adresses (`javascript:`, `intent:`, `tel:`…) sont ignorées. Les cadres ne sont pas limités.
- **Données** : JavaScript, stockage du DOM et service worker (par défaut) restent actifs ; les cookies, dont celui de rafraîchissement du jeton (`HttpOnly`), sont écrits sur le disque à chaque `onPause` : la session survit à la fermeture de l'application. Contenu mixte refusé, Safe Browsing actif, aucun cookie tiers, aucun accès aux fichiers. Le drive a son **propre profil de WebView** (`DriveProfile`, fonction `MULTI_PROFILE` de `androidx.webkit`) : la WebView de Repas ne reçoit ni l'agent Leclerc ni les cookies de Leclerc, et « Se déconnecter de Leclerc » n'efface que le drive. Sur une WebView sans profils, le drive partage les données de Repas et la fenêtre de confirmation prévient que Repas sera déconnecté aussi.
- **Confort** : bouton retour = retour arrière dans le front, puis sortie ; page d'erreur en français avec « Réessayer » (hors connexion, serveur muet, certificat refusé) ; marges sous les barres du système (`targetSdk` 36) ; barre d'état et fond aux couleurs du thème clair ou sombre du système (`res/values*/themes.xml`, jetons « Basilic & safran » du front) ; icône adaptative (feuille de basilic sur fond basilic, nervure safran, icône thématique d'Android 13) et écran de lancement basilic (Android 12 et plus : `windowSplashScreen*` ; avant : `launch_background`), sans image externe.
- **Pas de sélecteur de fichiers** : le front n'envoie ni fichier ni photo (`__tests__/shell.spec.ts` échoue si un champ `type="file"` apparaît dans `src/`), donc ni `onShowFileChooser`, ni permission de stockage ou de caméra. Une seule permission : Internet.
- **Menu** : il s'ouvre par le message `app.menu` du pont (le front le déclenche par l'entrée « Menu de l'application » de sa page « Moi », visible seulement dans l'application : DRV-320) ; la variante de débogage a en plus un bouton ⋮ sur le bord droit. Entrées : « Réglages du drive » (charge `/drive/reglages` du front), « Ouvrir le drive Leclerc » (`DriveActivity`, pour se connecter à Leclerc à l'avance), « Version et mode d'emploi », « Se déconnecter de Leclerc ».
- **Liens entrants** : un lien `https://<hôte de Repas>/…` reçu d'une autre application (courriel de confirmation d'adresse) s'ouvre dans la coquille (`launchMode="singleTask"`, `onNewIntent`). Le filtre d'intention porte `autoVerify="true"`.

### Étape humaine : publier `assetlinks.json` (liens vérifiés)

Sans ce fichier, Android ne vérifie pas le lien : un lien `https://kantin.eu/…` s'ouvre dans le navigateur (ou propose le choix) au lieu de l'application. À faire **avant la première version signée** (DRV-315 ; le workflow de publication refuse de publier tant que `public/.well-known/assetlinks.json` n'existe pas, car il y lit l'empreinte attendue du certificat), par l'humain et l'assistant. Le pas à pas est dans [`PUBLICATION.md`](PUBLICATION.md), étapes 2 et 4 ; en résumé :

1. récupérer l'empreinte SHA-256 du certificat de signature de publication : `keytool -list -v -keystore <fichier de clé> -alias <alias>` (ligne « SHA256 »), ou `apksigner verify --print-certs android/dist/repas-drive.apk` ;
2. publier `https://kantin.eu/.well-known/assetlinks.json` (code 200, `application/json`, **sans redirection**, accessible sans identification) avec ce contenu, l'empreinte remplaçant l'indication :

   ```json
   [
     {
       "relation": ["delegate_permission/common.handle_all_urls"],
       "target": {
         "namespace": "android_app",
         "package_name": "eu.kantin.repas.drive",
         "sha256_cert_fingerprints": ["<EMPREINTE SHA-256 DU CERTIFICAT DE PUBLICATION>"]
       }
     }
   ]
   ```

   Côté front, le fichier va dans `public/.well-known/assetlinks.json` ; l'empreinte du certificat n'est pas un secret. **Essayé sur l'image de production** : Vite le recopie dans `dist/.well-known/`, le Caddy du front (`try_files {path} /index.html`) le sert en `200` et `application/json`, sans redirection, et la bordure du back (`deploy/Caddyfile`) envoie tout ce qui n'est pas `/api` ni `/images` vers le front : **aucun changement dans `deploy/`**. Fichier absent, Caddy répond `200` avec la page d'accueil : contrôler le type (`curl -sSI`), pas seulement le code. `__tests__/publication.spec.ts` vérifie la forme du fichier (un seul paquet `eu.kantin.repas.drive`, empreintes en `AA:BB:…`, jamais celle de la clé de débogage).
3. vérifier : `adb shell pm get-app-links eu.kantin.repas.drive` (état `verified` pour l'hôte), ou ouvrir un lien reçu par courriel.

**Ne jamais** y mettre l'empreinte de la clé de débogage (publique) : n'importe qui pourrait alors se faire passer pour l'application. L'APK de débogage ne sera donc jamais « vérifié » : c'est voulu.

### Le pont natif `repasNative` (DRV-317)

`WebViewCompat.addWebMessageListener`, nom `repasNative`, **origine autorisée : celle de Repas seulement** (`setOf(REPAS_ORIGIN)`), page principale seulement ; **aucun `addJavascriptInterface`**. Sans la fonction (WebView très ancienne), l'objet n'existe pas : le front doit tester sa présence. Côté page :

```js
const native = window.repasNative // undefined hors de l'application
native.addEventListener('message', (event) => handle(JSON.parse(event.data))) // AVANT le premier message
native.postMessage(JSON.stringify({ v: 1, type: 'app.info' }))
```

Messages : JSON en **texte**, `v: 1` et `type`, **64 Ko au plus** (octets UTF-8) dans le sens page vers application. L'application répond sur le même canal ; le canal de réponse est celui de la page courante et disparaît quand la page se recharge (la nouvelle page le retrouve par son premier message).

| De la page vers l'application | Réponse |
|---|---|
| `{"v":1,"type":"app.info"}` | `{"v":1,"type":"app.info","version":"1.2.3","versionCode":42,"drive":true}` : `version` et `versionCode` de l'application ; `drive` : faux si l'agent embarqué est absent, altéré ou si la WebView est trop ancienne |
| `{"v":1,"type":"app.menu"}` | aucune : le menu de l'application s'ouvre |
| `{"v":1,"type":"drive.start","plan":{…}}` | voir « Le passage du plan » ci-dessous |
| `{"v":1,"type":"drive.setup","runId":"<uuid>"}` | voir « La lecture du magasin » ci-dessous |
| `{"v":1,"type":"drive.cancel"}` (`runId` facultatif) | voir « Le passage du plan » ci-dessous |
| tout autre message | `{"v":1,"type":"error","code":"INVALID_MESSAGE"}` (pas du texte, plus de 64 Ko, pas du JSON objet, `v` différent de 1) ou `{"v":1,"type":"error","code":"UNKNOWN_TYPE"}` (type inconnu) |

Un message d'une autre origine ou d'un cadre secondaire n'est jamais livré à l'application (le canal n'existe pas pour lui) ; s'il arrivait, il est ignoré sans réponse et seule la raison est notée au journal (jamais le contenu).

### Le passage du plan (DRV-314)

`drive.start` fait passer une liste de Repas au drive Leclerc ; `drive.result` ramène ce que l'agent en a fait.

| Message | Sens | Forme et effet |
|---|---|---|
| `drive.start` | page vers application | `{"v":1,"type":"drive.start","plan":<message `plan` du protocole v1>}`. L'application valide la **forme** du plan (`v` 1, `type` `plan`, `runId` UUID, `retailer` `leclerc`, magasin `{id, host}` avec un identifiant de 1 à 12 chiffres et un hôte `*.leclercdrive.fr` en minuscules, `returnPath` `/drive/retour`, 100 lignes au plus, message de 64 Ko au plus) sans lire les lignes, ouvre `DriveActivity` sur **l'accueil de l'enseigne**, `https://www.leclercdrive.fr/` (`NavigationPolicy.START_URL`, comme `drive.setup` ; session ouverte il affiche l'accueil du magasin de l'utilisateur ; la racine de l'hôte du magasin, `https://<hôte>/`, et `/magasin-<id>-<id>/` sont des pages 404 du vrai site), et envoie le plan à l'agent quand la page a annoncé l'agent, fini de charger **et** que c'est une page de magasin (`NavigationPolicy.isStorePage`), donc quand l'utilisateur a touché lui-même « Commencer mes courses » ; en attendant, un bandeau en haut de l'écran dit « Ouvre ton magasin sur Leclerc… » (`StoreBanner.OPEN`), et si le site refuse la page, tarde ou n'a pas d'agent, « Cette page n'est pas celle de ton magasin… » avec le bouton « Ouvrir l'accueil du drive » (`OpeningWatch`, voir « Le repli quand la page du magasin n'est pas celle attendue »). Pas de réponse en cas de succès : la suite est `drive.result`. Le même `runId` renvoyé pendant un passage rouvre l'écran du drive sans rien recommencer. |
| `drive.cancel` | page vers application | `{"v":1,"type":"drive.cancel"}` ou avec `"runId":"<uuid>"` (qui doit être celui du passage en cours). Le passage prend fin par un `drive.result` d'issue `aborted`. |
| `drive.result` | application vers page | `{"v":1,"type":"drive.result","result":<message `result` du protocole v1>}`. Le résultat de l'agent tel quel (même `runId`), ou, après un abandon (de l'utilisateur ou `drive.cancel`), `{"v":1,"type":"result","runId":…,"agentVersion":…,"outcome":"aborted","store":{"id":…},"error":{"code":"CANCELLED","message":"Envoi abandonné."},"lines":[]}` (aucune ligne : l'application ne sait pas ce que l'agent avait déjà mis au panier). L'enveloppe peut dépasser 64 Ko de quelques dizaines d'octets : la borne ne vaut que de la page vers l'application. |
| `drive.error` | application vers page | `{"v":1,"type":"drive.error","code":…,"runId"?:…}` : refus d'un message `drive.*`. `INVALID_PLAN` (le plan n'a pas la forme exigée ou son hôte n'est pas autorisé), `BUSY` (un autre passage est en cours, `runId` est le sien), `UNAVAILABLE` (le drive n'est pas utilisable : agent absent ou altéré, WebView trop ancienne ; `runId` du plan), `NO_PASS` (`drive.cancel` sans passage en cours). |

- **Un seul passage à la fois.** Un second plan (ou une lecture du magasin) reçoit `BUSY`. Le passage prend fin par le `result` de l'agent (du bon `runId`), par l'abandon (retour au bout de l'historique du drive, « Abandonner l'envoi » du menu du drive, `drive.cancel`, « Abandonner » à la reprise), ou au bout de 24 h.
- **Livraison du résultat.** `drive.result` est posté à la page de Repas par le canal de réponse de la page courante, **après** la réponse à tout message qu'elle envoie, et dès que la coquille revient au premier plan. Si la page s'est rechargée ou que l'application a été tuée entre-temps, le résultat reste en file (`DrivePass`, préférences privées de l'application) et est livré après le premier message de la nouvelle page. **Le front enregistre donc son écouteur `message` avant d'envoyer quoi que ce soit** (`driveBridge.listen()` au démarrage), et envoie `app.info` à chaque démarrage pour recevoir un résultat en attente.
- **Reprise (24 h).** Un passage de Repas non terminé (application fermée ou tuée) est gardé avec son `runId` et son plan (jamais un cookie), sans le résultat de l'agent. À la réouverture de la coquille, une fenêtre propose « Reprendre » (le drive se rouvre, le plan repart à l'agent, qui reprend par son état de session s'il l'a encore) ou « Abandonner » (résultat `aborted`). Passé 24 h le passage est oublié sans prévenir Repas.
- **Écran allumé** seulement pendant un passage, et seulement quand l'écran du drive est au premier plan.
- **Plan d'essai (débogage).** Le menu « Plan d'essai (débogage) » du drive passe par le même chemin (un seul passage à la fois, écran allumé, `DrivePass`) mais n'est jamais écrit ni livré à Repas : son résultat s'affiche dans l'écran de texte copiable.
- **Retour d'un passage de Repas.** À la réception du `result`, `DriveActivity` se referme et rend la main à la coquille (`MainActivity` rouverte au premier plan, recréée si Android l'avait fermée), qui livre `drive.result`.

### Entrer, revenir et finaliser sans geste (DRV-625)

- **Entrer** : le plan part vers l'agent aussi depuis l'**accueil de l'enseigne** (`NavigationPolicy.isHomePage`, `OpeningWatch.canDeliver(url, entersStore = true)`, jamais pour la lecture du magasin) ; l'agent y suit lui-même « Commencer mes courses » (une fois, `drive-agent/src/leclerc/entry.ts`), la page du magasin se charge et le plan repart. Sur l'accueil le bandeau de l'application se tait (`StoreBanner` : `NONE`) : l'agent dit « Ouverture de ton magasin… » ou, s'il ne peut pas, « Touche « Commencer mes courses ». ». Ailleurs, le bandeau `OPEN` reste : « Touche « Commencer mes courses ». » (rien sur la connexion : Leclerc exige un magasin choisi AVANT la connexion, et c'est l'agent qui demande de se connecter, seulement quand elle manque : « Tu n'es pas connecté à Leclerc… »). Sur la page de connexion hors d'un magasin, c'est `STORE_FIRST` (voir plus bas). L'application ne clique toujours pas : c'est l'agent.
- **Revenir** : à un envoi terminé sans rien à lire, l'agent poste le résultat tout de suite ; `DriveActivity.endOfPass` ferme le drive et ramène la coquille (rien à changer côté application).
- **Finaliser** : « Finaliser sur Leclerc » est un lien du front vers le drive. La coquille ne le confie plus au navigateur : `MainActivity` demande `DriveEntry.target(url)` (une page du drive : l'accueil, ou une page de magasin ; toute autre page du drive est remplacée par l'accueil) et ouvre `DriveActivity` avec `EXTRA_START_URL` (sans passage en cours, c'est le drive à parcourir à la main, connecté). Aucun message nouveau sur le pont : une application plus ancienne ouvre toujours le navigateur, sans dégât. **DRV-631** : la page `…/detail-panier.aspx` du vrai site s'ouvre « introuvable » quand on n'y arrive pas depuis le site de Leclerc : l'application n'y navigue **jamais**. Le front fait le lien `https://<hôte>/magasin-N-N` depuis le magasin enregistré (hôte et numéros seulement, `finalizeLink`, dans un navigateur l'accueil du drive) ; la coquille le complète : `StorePathMemory` retient, à la fin de chaque page de magasin que le drive a chargée sans erreur (`DriveActivity.onPageFinished`), le chemin `https://<hôte>/magasin-N-N-Ville` (motif `^/magasin-\d+-\d+-[^/]+$`, hôte `*.leclercdrive.fr` hors site mobile, préférence privée `drive-store`, exclue des sauvegardes, effacée par « Se déconnecter de Leclerc »). `DriveEntry.resolve(url, memory)` ne complète que le lien exact du magasin, **seulement** si l'hôte et les deux numéros sont ceux du chemin retenu : la page qui s'ouvre est l'accueil du magasin avec la ville (qui charge toujours) ; sinon, ou pour toute autre adresse du drive, l'accueil du drive. Le bandeau `StoreBanner.BASKET` (« Ton panier est dans l'icône en haut à droite. », sans bouton) accompagne l'arrivée et disparaît à la première navigation (`doUpdateVisitedHistory`). Jamais une adresse tirée du message du plan (`DriveEntry` et `StorePathMemory` ne lisent pas `DrivePlan` : `android/__tests__/basket-link.spec.ts`). Si le site refuse l'accueil du magasin (HTTP 4xx ou 5xx, sauf 403 et 429 qui sont le plus souvent le défi de l'anti-robot, à laisser passer) ou le sert avec un statut 200 et un titre « introuvable » (`WebChromeClient.onReceivedTitle` : seul le titre est lu, jamais le contenu de la page ; `DriveEntry.isNotFoundTitle`), `DriveActivity` se replie une fois sur l'accueil du drive (`DriveEntry.fallsBack`). La forme du dernier « Finaliser » (`FinalizeOutcome` : `OUVERTE`, `CHEMIN_INCONNU`, `ADRESSE_REFUSEE`, `ERREUR_HTTP_4XX`, `ERREUR_HTTP_5XX`, `TITRE_INTROUVABLE`) est gardée dans la préférence privée `drive-store` (clé `finalize`, effacée par « Se déconnecter de Leclerc ») et montrée dans « Version et mode d'emploi » : un mot, jamais une adresse, un numéro ni une ville. Aucun message nouveau sur le pont. Les deux ordres de publication sont sans dégât : une application ancienne qui reçoit le nouveau lien, ou l'inverse, ouvre l'accueil du drive.

### L'ouverture d'un plan et le repli (ticket E de l'audit du 2026-10-18)

**Constat de la recette réelle** : `https://<hôte>/magasin-<id>-<id>/` (la page ouverte par la PR #125) et la racine de l'hôte du magasin `https://<hôte>/` (la page ouverte par la PR #128) sont des pages 404 du vrai site ; l'accueil de l'enseigne `https://www.leclercdrive.fr/`, session ouverte, affiche l'accueil du magasin avec le bouton « Commencer mes courses », qui mène aux vraies pages du magasin. Un plan s'ouvre donc sur l'**accueil de l'enseigne** (`DrivePlan.startUrl` = `NavigationPolicy.START_URL`, comme la lecture du magasin), jamais sur une adresse de l'hôte du magasin. Ce n'est pas une page de magasin pour l'agent : l'utilisateur touche lui-même « Commencer mes courses » (**l'application ne clique jamais à sa place**) et le plan part tout seul vers l'agent dès qu'une page de magasin est atteinte (si ce n'est pas le magasin du plan, l'agent répond `STORE_MISMATCH`, « Ce n'est pas le bon magasin »). Dans tous les cas l'utilisateur ne reste jamais devant un écran muet :

- **`StoreBanner`** : le bandeau d'en-tête, **au-dessus** de la page et du panneau d'incident (un 5xx montre les deux). `OPEN` pendant l'attente normale (« Touche « Commencer mes courses ». », sans alarme ni bouton, sans un mot sur la connexion) ; `STORE_FIRST` (recette réelle du 2026-10-19 : Leclerc exige un magasin choisi AVANT la connexion et refuse sinon avec « Avant de vous authentifier, veuillez sélectionner un Drive. ») quand la page de connexion s'affiche avant tout magasin, pour un envoi comme pour la lecture du magasin (« Choisis d'abord ton magasin : touche la flèche retour de la page, puis choisis-le. », sans bouton) : `NavigationPolicy.isLoginPage` ne lit que l'**adresse** (`/connexion` ou `/connexion.aspx` sur le drive, hors site mobile et hors du chemin d'un magasin `/magasin-N-N…`), jamais le contenu de la page ; le message rouge de Leclerc, lui, n'a pas d'adresse à lui et n'est pas détecté (lire le texte de la page serait une détection fragile) ; une adresse de connexion que le vrai site utiliserait autrement ne déclenche simplement pas ce bandeau ; `PLAN` quand le site refuse la page, tarde ou n'a pas d'agent (« Cette page n'est pas celle de ton magasin : Leclerc l'a refusée ou ne répond pas. Touche « Ouvrir l'accueil du drive » pour recommencer. ») avec le bouton **« Ouvrir l'accueil du drive »** (recharge `PassRequest.startUrl`, donc l'accueil de l'enseigne, pas la page 404) ; `VERIFICATION` (403 ou 429, souvent le défi de l'anti-robot : la page reste visible, le bouton reste proposé) ; `MOBILE` (ticket J de l'audit du 2026-10-18, hypothèse H11 : la page est le **site mobile** `m-courses.leclercdrive.fr`, « Leclerc affiche son site mobile : ce n'est pas la version ordinateur du site, et Repas ne peut pas y agir. Touche « Ouvrir l'accueil du drive » pour recommencer. », avec le bouton ; `NavigationPolicy.isMobileSite` reconnaît le premier nom `m` ou `m-…`, et `isStorePage` est **faux** pour lui même avec une adresse `/magasin-N-N…` : l'application ne lui envoie donc **jamais** un plan ni la lecture du magasin, `OpeningWatch.canDeliver` non plus ; la page reste dans l'application, seul l'agent n'y agit pas ; la WebView est en mode ordinateur pour ne pas le recevoir, ce bandeau n'est que le repli) ; `SETUP` pour la lecture du magasin (« Choisis ton magasin, puis touche « Utiliser ce magasin ». Le bouton retour du téléphone annule. » : le magasin d'abord, la connexion n'y est pas nécessaire et n'y est pas citée). Garde : `src/i18n/__tests__/store-before-login.spec.ts` échoue si un texte de lecture du magasin parle de connexion avant le magasin.
- **`OpeningWatch`** (Kotlin pur, `OpeningWatchTest`) suit la page principale et rend un `PageTrouble` : début et fin de chargement, statut HTTP (`onReceivedHttpError`), échec de chargement (`onReceivedError` : le panneau d'incident l'explique déjà), plan parti vers l'agent, et deux délais armés par l'activité : **25 s** de chargement (`LOAD_TIMEOUT_MS`) et **10 s** après la fin d'une page de magasin pour que l'agent s'annonce et reçoive son message (`AGENT_TIMEOUT_MS`). `VERIFICATION` (403, 429), `HTTP_ERROR` (toute autre erreur 4xx ou 5xx), `SLOW`, `NO_AGENT`, `NONE`. Le plan ne part **jamais** vers une page que le site a refusée. **Piège constaté dans l'émulateur** : la WebView annonce l'erreur HTTP de la page principale **avant** `onPageStarted` (qui a lieu à la validation de la navigation) : le début d'une page ne doit pas effacer l'erreur déjà annoncée (`pageStarted` ne remet à zéro que si la page n'est pas déjà commencée ; `restart` pour les ouvertures de l'application, `shouldOverrideUrlLoading` aussi).
- **Les 404 de la recette réelle** (la racine de l'hôte du magasin, `/magasin-<id>-<id>/`) tombent dans `PageTrouble.HTTP_ERROR` comme toute erreur 4xx ou 5xx de la page principale, que l'utilisateur y arrive par un lien, une redirection ou le départ lui-même : le bandeau `PLAN` et son bouton s'affichent, le plan ne part pas, et le bouton recharge l'accueil de l'enseigne. Une page « introuvable » servie avec le statut 200 ne serait pas vue (l'application ne lit pas le contenu des pages) : à confirmer sur le vrai site.
- Garde : `OpeningWatchTest`, `StoreBannerTest` (une 404 sur ces adresses donne le repli), `DrivePlanTest` (l'accueil de l'enseigne, jamais la racine de l'hôte du magasin ni `/magasin-N-N/`), `NavigationPolicyTest` (de l'accueil de l'enseigne à la page du magasin, chaque étape reste dans l'application), scénarios 2 et 8 à 12 de `make android-e2e` (le faux site : racine de l'hôte du magasin et `/magasin-N-N/` en 404, accueil sur `www.leclercdrive.fr`, les défauts `homeStatus` (404, 403…), `homeDelayMs` et `startPath`, et « Changer de magasin ») ; `__tests__/emulator-e2e.spec.ts` tient ensemble la constante de l'application, le faux accueil et les scripts.
- **Mémoriser l'adresse réelle du magasin (ticket F, étudié, non fait)** : la base ne garde que `…/magasin-N-N` (`baseUrl`, sans ville). L'adresse réelle que l'agent observe à la lecture du magasin (`setup`) porte la ville, mais ni le protocole ni la base ne la transportent. Trois pistes, de la moins coûteuse à la plus coûteuse : (1) **côté application seulement** (aucun changement de contrat) : la coquille retient, en préférences privées du téléphone, le chemin de la première page de magasin que l'utilisateur ouvre pour un plan (sans paramètres), et l'ouvre directement la fois suivante, avec l'accueil de l'enseigne en repli (le bandeau `PLAN` rattrape un 404) ; (2) un champ **facultatif** `entryPath` dans `store` du `setup-result` et du plan (protocole v1 additif, colonne côté back) ; (3) rien : l'accueil de l'enseigne suffit (un toucher de plus). Rien n'est mesuré sur la forme de l'adresse d'arrivée : le diagnostic en donne le motif (`/magasin-N-N-V/…`, ticket B).

### La lecture du magasin (DRV-320)

`drive.setup` fait choisir son magasin à l'utilisateur sur le drive et le fait lire par l'agent ; le front n'en tire que l'identifiant et l'adresse du magasin (jamais d'identifiant ni de cookie Leclerc). C'est un passage comme un autre (même file, même unicité, même abandon, même reprise sous 24 h) dont la demande est un message `setup` du protocole v1 **sans `store`**.

| Message | Sens | Forme et effet |
|---|---|---|
| `drive.setup` | page vers application | `{"v":1,"type":"drive.setup","runId":"<uuid>"}` (rien d'autre n'est lu). L'application ouvre `DriveActivity` sur l'accueil du drive (`https://www.leclercdrive.fr/`) avec, en haut de l'écran, le message « Choisis ton magasin, puis touche « Utiliser ce magasin ». Le bouton retour du téléphone annule. » (le magasin d'abord : Leclerc refuse la connexion tant qu'aucun magasin n'est choisi, voir `StoreBanner.STORE_FIRST`). L'utilisateur choisit lui-même son magasin sur le site. **Le message `setup` n'est envoyé à l'agent que lorsque la page est celle d'un magasin** (`https`, `*.leclercdrive.fr`, chemin `/magasin-<id>-<id>[-Ville]/…`, `NavigationPolicy.isStorePage`), une fois la page chargée et l'agent annoncé ; le message disparaît alors, l'agent lit le magasin dans l'adresse de la page (aucune requête), demande « Utiliser ce magasin ? » et renvoie un `setup-result`. Le même `runId` renvoyé pendant la lecture rouvre l'écran du drive. |
| `drive.result` | application vers page | `{"v":1,"type":"drive.result","result":<setup-result>}` : `{"v":1,"type":"setup-result","runId":…,"agentVersion":…,"store":{"id","host","baseUrl","label"}}` (`label` est `null` : l'agent ne lit pas le nom du magasin). Ou un `result` d'issue `aborted` (abandon : retour au bout de l'historique du drive puis « Abandonner », « Abandonner la lecture du magasin » du menu du drive, `drive.cancel`, ou « Annuler » dans l'écran de l'agent) ou `error` (`UNSUPPORTED_PAGE`, `STORE_MISMATCH`…), **sans `store`** quand le magasin n'est pas connu (le `store` d'un `result` est facultatif depuis DRV-320). |
| `drive.error` | application vers page | `BUSY` (un autre passage est en cours, `runId` est le sien), `INVALID_SETUP` (`runId` absent ou qui n'est pas un UUID), `UNAVAILABLE` (agent absent ou altéré, WebView trop ancienne ; `runId` de la lecture). `NO_PASS` et `drive.cancel` valent aussi pour une lecture. |

- Si le `setup` porte un `store` (un autre appelant que le front), la page doit être celle de ce magasin, sinon l'agent répond `STORE_MISMATCH` ; le front de Repas n'en envoie pas.
- Une lecture interrompue (application fermée ou tuée, moins de 24 h) se reprend ou s'abandonne à la réouverture, avec ses propres textes (« Lecture du magasin interrompue »).
- Le menu de débogage « Plan d'essai » envoie aussi un `setup` sans magasin à l'agent avant le plan.

## La lisibilité en mode ordinateur

**Le défaut (recette réelle, 2026-10-18).** Le drive s'affiche en mode ordinateur (voir « Règles du domaine » du skill : sinon Leclerc sert son site mobile, aux routes que l'agent ne gère pas). La fenêtre de la page fait alors ~980 px CSS, affichée sur ~411 dp d'écran : un pixel CSS ne mesure plus que 0,42 dp. Le texte de l'interface de l'agent (16 px) faisait 6,7 dp et ses boutons (44 px) 18 dp, dans le coin d'un écran presque vide : « Utiliser ce magasin ? », le récapitulatif, le choix de produit étaient illisibles et intouchables. Les faux sites de l'émulateur cachaient le défaut (`<meta name="viewport" content="width=device-width">`, fenêtre de 411 px) et l'émulateur avait un écran de 360 dp : ils n'ont plus de balise `viewport` et l'émulateur est un Pixel 9.

**Mesuré dans la WebView de l'émulateur configuré en Pixel 9** (WebView 113, `make android-e2e` écrit ces valeurs dans son rapport) : `window.innerWidth` 980, `screen.width` 412, `devicePixelRatio` 2,625, `visualViewport.scale` 0,4207 (les dp par pixel CSS, zoom initial de la fenêtre large compris), partie visible 980 × 2016 px CSS. En paysage : `innerWidth` 980, `screen.width` 924, mais `visualViewport.scale` 0,89 (la WebView n'occupe que ~872 dp : barres et encoche). **Facteur d'échelle de l'interface de l'agent obtenu : 2,377** (1 / 0,4207) ; son cadre mesure 412,19 px CSS de large avant agrandissement, la largeur de l'écran en dp.

| Mesuré à l'écran (Pixel 9) | Avant | Après |
|---|---|---|
| texte courant de l'interface | 6,7 dp | 16 dp |
| bouton « Commencer » (hauteur) | 18 dp | 48 dp |
| cibles tactiles de la liste de produits | 20 dp | 48 dp |
| interface | dans le haut-gauche d'un écran presque vide (cadre de 980 px CSS) | sur toute la largeur de l'écran, à la taille d'une page de téléphone |

**Côté agent** (voir `drive-agent/README.md`, « Échelle d'affichage » ; `drive-agent/src/ui/scale.ts`) : l'interface s'agrandit de 1 / `visualViewport.scale` (entre 1 et 3 ; 1 sur un écran d'ordinateur ou une page de téléphone), se pose sur la zone visible de la page (même si l'utilisateur l'a agrandie au pincement) et suit les changements d'affichage. L'application n'y a rien à faire : c'est ce qui rend sûr tout réglage de zoom de la WebView.

**Côté WebView du drive** (`DesktopMode`, `DriveActivity`) : **aucun réglage de zoom ne change**. Fenêtre large + vue d'ensemble (`useWideViewPort`, `loadWithOverviewMode`), pincement et double toucher (zoom sur le bloc touché : essayé dans l'émulateur, la page passe de 0,42 à 0,50 dp par pixel CSS) restent permis ; **le menu du drive gagne « Agrandir la page » et « Réduire la page »** (`WebView.zoomBy`, ×1,5 par cran, borné par la WebView ; le coin haut gauche de ce que l'on voyait reste en place, au lieu du zoom autour du centre de l'écran qui ferait sortir le haut de la page : 0,42, puis 0,63, puis 0,95 dp par pixel CSS mesurés dans l'émulateur) pour ceux qui ne pincent pas. Choisi parce que c'est l'option la moins risquable pour l'agent et la navigation :

- `textZoom` et `LayoutAlgorithm.TEXT_AUTOSIZING` changeraient aussi la taille du texte de l'interface de l'agent (qui se mesure et se corrige déjà) et refont la mise en page d'un site que l'on ne peut pas ouvrir ici (texte coupé, débordements) : on ne peut ni les mesurer sur le vrai site (interdit), ni les défaire sans nouvelle version ;
- `setInitialScale` cache une partie de la largeur de la page derrière un défilement horizontal, sur une mise en page inconnue, et change ce que l'utilisateur voit à chaque page ;
- le zoom de la page reste donc un geste de l'utilisateur (pincement, double toucher, menu), jamais un réglage invisible. Si la recette réelle montre que le site de Leclerc reste trop petit, un réglage se choisit à ce moment-là, avec le site sous les yeux (et l'agent s'y adapte déjà).

**Contrôles** : `make android-e2e` (scénario 2) lit dans l'arbre d'accessibilité d'Android la hauteur en dp de « Commencer », « Annuler », « Choisir » et « Pas cette fois » (44 dp au moins, dans la largeur de l'écran) et le facteur de l'interface par le débogage à distance (`display.mjs`, APK de débogage seulement) ; `make android-smoke` vérifie « Agrandir la page » et « Réduire la page » sur la page du faux drive. Les captures `e04` et `e05` de `android/dist/e2e/` sont à lire.

## L'agent embarqué (DRV-313)

- **Un actif de l'APK.** `drive-agent/dist/agent.js` (construit par `make agent-build`) est copié dans l'application à la construction (tâche Gradle `prepareAgentAsset`), qui **échoue** si son empreinte SHA-384 n'est pas celle de `agent.js.sha384`. Une modification de l'agent (ou de sa chaîne de construction) change l'empreinte : `make android-agent-hash`, relire, commiter le fichier et le dire dans la PR. `make check` le détecte aussi (`__tests__/agent-asset.spec.ts` compare le fichier, une construction fraîche et `manifest.json`). À l'exécution l'application revérifie l'empreinte avant d'injecter quoi que ce soit (`AgentAsset`) ; un agent absent ou altéré n'est jamais injecté et la fenêtre « Version » le dit.
- **Injection.** `WebViewCompat.addDocumentStartJavaScript` évalue `injection.js` (le pont, puis l'agent) avant tout script des pages `https://*.leclercdrive.fr`, jamais `*` ; si la WebView ne l'offre pas, repli par `evaluateJavascript` après `onPageFinished`, pour les mêmes pages. L'agent ne démarre que dans la page principale (un cadre, comme le défi anti-robot, n'en reçoit pas), une seule fois, et reste silencieux tant qu'aucun message n'arrive.
- **Canal.** `WebViewCompat.addWebMessageListener`, nom `repasHost`, mêmes origines. **Pas de `addJavascriptInterface`.** `injection.js` remplace l'objet natif par un objet gelé à la forme exacte qu'attend l'agent (`postMessage(texte)` et `addEventListener('message', …)`, voir `bridgeTransport`), garde en file les messages arrivés avant l'agent, et annonce la page par un premier message `{"v":1,"type":"hello"}` : c'est lui qui donne à l'application le canal de réponse vers cette page, par lequel partent tous ses messages (le canal natif n'en a pas d'autre).
- **Messages.** JSON du protocole v1, en texte, 64 Ko au plus dans les deux sens. Application vers agent : `plan`, `setup`, `command` (`diagnostic`, et `selftest` en débogage). Agent vers application : `result`, `setup-result`, `selftest-result` (`progress` et `log` sont acceptés mais l'agent n'en envoie pas encore). `BridgeMessages` ignore, en n'écrivant au journal que la raison, tout message d'une origine autre que `https://<sous-domaine>.leclercdrive.fr`, d'un cadre secondaire, qui n'est pas du texte, trop gros, qui n'est pas du JSON objet de version 1 ou de type inconnu. L'application ne les interprète pas, sauf `result` pendant un passage (DRV-314 : il est livré à Repas).
- **Mode débogage.** `injection.js` porte un marqueur `/*__DEBUG__*/false` que `AgentAsset.assemble` remplace par `true` dans la variante de débogage (`BuildConfig.DEBUG`) et par `false` partout ailleurs. À `true`, le pont de la page porte `isDebug` (gelé) et le message d'accueil devient `{"v":1,"type":"hello","debug":true}` : seul cas où l'agent honore la commande `selftest`. `AgentHost.openSelftest()` n'envoie la commande que si l'application est la variante de débogage et si la page a annoncé `debug: true`.
- **Diagnostic de l'agent.** L'entrée du menu envoie `{"v":1,"type":"command","command":"diagnostic"}` ; l'agent ouvre son écran de diagnostic dans la page. Jamais de fragment d'adresse sur les pages du drive.
- **Plan d'essai (variante de débogage seulement).** `BuildConfig.DEBUG` ajoute au menu « Plan d'essai (débogage) » : l'application envoie `setup` (l'agent lit le magasin de la page et demande de le confirmer), puis un plan synthétique de quatre ingrédients (`src/debug/assets/debug-plan.json`, validé par `validatePlan` dans `__tests__/debug-plan.spec.ts`, sans produit mémorisé, avec `needed`), puis montre le résultat de l'agent dans un écran de texte copiable (numéro de magasin réduit à ses trois derniers chiffres, ni libellé, ni adresse, ni cookie). L'APK de publication n'a ni ce menu ni ce fichier.
- **Test automatique (variante de débogage seulement, DRV-318).** « Test automatique (débogage) » remplace la procédure manuelle d'une trentaine d'essais : un seul geste, un seul rapport. L'application vérifie qu'une page du drive est ouverte, envoie la commande `selftest` ; l'agent enchaîne sans autre action le diagnostic (huit contrôles, plus les sondes du site réel du ticket B : formes, noms et nombres seulement, dont le POURQUOI d'une recherche en échec), la lecture du magasin, un lot de 12 recherches en série, puis un essai de 3 produits (premier candidat en stock pour trois exemplaires, hors panier ; quantité 1, puis 3 puis 2 sur le premier, puis retrait de tout et comparaison du panier avant et après), à la cadence normale (800 ms + gigue). Garde-fous : 3 produits au plus, quantité 3 au plus, arrêt immédiat sur blocage, nettoyage toujours tenté. L'agent rend un message `selftest-result` (le rapport en texte) ; `SelftestRun` ne l'accepte que si l'application vient de le demander ; `SelftestReport` le revérifie et masque tout de même adresses, e-mails et numéros de six chiffres ou plus ; `TextPanel` le copie dans le presse-papiers à l'ouverture, avec « Copier » et « Partager ». Mode d'emploi pour l'utilisateur : `PROCEDURE.md`.

## Version

- Le **nom** (`1.2.3`) vient de l'étiquette Git `android-v1.2.3` : variable `ANDROID_VERSION_TAG` (format strict `android-vX.Y.Z`).
- Le **code** (l'entier que le système compare pour accepter une mise à jour, qui ne doit jamais baisser) vient, pour une publication, **de la même étiquette** : `X * 1 000 000 + Y * 1 000 + Z` (`android-v1.2.3` donne 1 002 003 ; `0.0.0` est refusé, Y et Z vont jusqu'à 999, X jusqu'à 2099). Il monte donc avec le numéro de version, sur n'importe quel ordinateur ; le workflow refuse une étiquette plus ancienne que la dernière publiée. Les constructions de **débogage** de la CI le tirent d'un compteur (`ANDROID_VERSION_CODE`, le numéro d'exécution) : leur clé n'est pas celle de la publication, les deux familles ne se mettent jamais à jour l'une l'autre. Pour une publication, `ANDROID_VERSION_CODE` ne sert plus ; s'il est donné, il doit être égal au code de l'étiquette.
- `ANDROID_COMMIT` (l'empreinte du commit, 7 caractères gardés) s'ajoute à la ligne de version ; `local` hors CI.
- Sans étiquette ni compteur (construction locale), la version est `0.0.0-dev` (code 1). Avec l'étiquette seule, le code en est tiré. Une valeur **présente mais invalide** est toujours refusée. Une **publication** (`make android-release`) exige l'étiquette : un APK signé nommé `0.0.0-dev` ou numéroté 1 empêcherait toute mise à jour par-dessus.
- La version est visible dans l'application, sur son écran : `Version 1.2.3 (numéro 42), construction 0123abc` (`, débogage` pour l'APK de débogage).

Exemples : `ANDROID_VERSION_TAG=android-v0.1.0 ANDROID_VERSION_CODE=7 make android` (débogage, code 7) ; `ANDROID_VERSION_TAG=android-v0.1.0 make android-release` (publication, code 1 000).

## Signature

- **APK de débogage** : signé avec `debug.keystore`, une clé jetable et publique reprise du spike. Elle ne protège rien et ne signe jamais une publication. Chaque APK de débogage s'installe par-dessus le précédent.
- **APK de publication** : signé avec une clé **fournie par variables d'environnement**, qui ne touche jamais le dépôt : `ANDROID_KEYSTORE_BASE64` (le fichier de clé encodé en base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` (les mêmes noms que les secrets GitHub du workflow `android-release.yml` ; pour un fichier PKCS12 les deux mots de passe sont identiques). Le script décode la clé dans un fichier temporaire du conteneur, effacé en sortie ; aucune valeur n'est affichée. La création de cette clé, sa sauvegarde, la pose des secrets GitHub et la publication d'`assetlinks.json` sont des **étapes humaines**, expliquées pas à pas dans [`PUBLICATION.md`](PUBLICATION.md).
- **Contrôle de l'APK** (`build.sh verify-release`, `make android-release-verify`) : l'empreinte SHA-256 du certificat doit être l'une de celles de `ANDROID_EXPECTED_CERT_SHA256` (publiques ; le workflow les lit dans `public/.well-known/assetlinks.json`) et n'est **jamais** celle de `debug.keystore` ; le paquet, le nom et le code de version sont ceux de l'étiquette (recalculés en bash, indépendamment du Kotlin) ; `minSdk` 26, `targetSdk` 36 ; **une seule permission** (Internet) ; non débogable ; pas de `assets/debug-plan.json` ; `BuildConfig.DEBUG` faux et origine `https://kantin.eu/` ; l'agent embarqué a l'empreinte de `agent.js.sha384`.
- Un APK de débogage et un APK de publication n'ont pas la même clé : Android refuse de l'un à l'autre. Désinstaller l'application avant de passer de l'un à l'autre.
- Jamais de clé, de mot de passe ni de secret dans le dépôt (public) : `.gitignore` ignore les fichiers de clé et `__tests__/hygiene.spec.ts` (joué par `make check`) le vérifie.

## Règles

- **Rien d'une enseigne n'est lu ni conservé** : aucun identifiant, cookie, jeton ni contenu de page dans les journaux ou le dépôt. L'utilisateur se connecte lui-même dans la WebView. Les cookies restent sur le téléphone (ni sauvegarde dans le nuage, ni transfert d'appareil : `data_extraction_rules.xml`).
- **Aucun objet natif exposé aux pages** (pas de `addJavascriptInterface`) : deux canaux de messages seulement, `repasNative` restreint à l'origine de Repas (DRV-317) et `repasHost` restreint à `*.leclercdrive.fr` (DRV-313). Le code qui tourne dans les pages du drive est `injection.js` et `agent.js`, tous deux dans l'APK et vérifiés : jamais de code reçu d'un site. L'agent n'est jamais injecté dans la WebView de Repas.
- **Une seule permission : Internet**. Jamais d'autre (pas de position, de fichiers, de caméra ni de contacts). `ACCESS_NETWORK_STATE` n'est pas demandée non plus : « hors connexion » se déduit de l'erreur de la WebView.
- **Données synthétiques** dans les tests : aucun vrai numéro de magasin, nom de ville, cookie ou HTML d'enseigne (dépôt public). Aucun essai ne contacte `leclercdrive.fr` depuis la CI : le site se visite seulement sur le téléphone de l'utilisateur (recette, DRV-505).
- `targetSdk` 36 : depuis Android 15 l'écran passe sous les barres du système (bord à bord). La racine de l'écran garde ses marges sous les barres du système, les encoches et le clavier (`setOnApplyWindowInsetsListener`) ; le spike restait en 34 pour éviter ce travail. Le geste « retour » passe par `OnBackInvokedCallback` (Android 13 et plus) : la méthode `onBackPressed` n'y est plus appelée.
- Gradle est lancé sans démon, plugins et dépendances épinglés (`build.gradle.kts`, `app/build.gradle.kts`), image de construction épinglée par empreinte (`Dockerfile`). Une mise à jour d'outil se fait à la main, une PR par chantier.
