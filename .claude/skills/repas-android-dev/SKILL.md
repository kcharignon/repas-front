# repas-android-dev — l'application Android

L'application affiche le drive Leclerc dans une **WebView en mode ordinateur**, y injecte l'agent (`drive-agent/dist/agent.js`) et lui parle par un canal restreint. Kotlin, deux modules : le **cœur** `android/core` (règles en Kotlin sans aucune classe Android) et l'**application** `android/app` (colle d'Android), AndroidX réduit au strict nécessaire, `applicationId` `eu.kantin.repas.drive`, `minSdk` 26, `targetSdk` 36. Tout se construit dans Docker (JDK, Gradle, SDK) : rien à installer sur la machine.

1. Lire `android/README.md` (commandes, structure, version, signature, émulateur), **`android/ARCHITECTURE.md` (le cœur sans Android et les services de plateforme, § 3c)**, `android/PROCEDURE.md`, `CLAUDE.md` du front, puis dans le dépôt back `kcharignon/repas` : `docs/drive/pivot-application-android.md`, `docs/drive/spikes/DRV-011-rapport.md` et `DRV-005-decision-g1.md`, `docs/drive/consignes-agents.md` et le ticket `docs/drive/tickets/DRV-31x-*.md` (sections « Réalisation », « Points laissés », « RÉVISION » : contrats pour la suite).
2. Règles transverses (détail : `consignes-agents.md` du back) : **aucun contact avec Leclerc** (aucun test, aucune émulation ouverte sur le vrai site : le vrai site se visite seulement sur le téléphone de l'utilisateur, recette DRV-505) ; aucune donnée réelle (valeurs factices `123456`, `Ville-Test`) ; jamais de déploiement, de release de production ni de secret ; une PR n'est fusionnée que si **tous** les contrôles de la CI sont verts ; commits courts en français **sans `Co-Authored-By`** ; worktree dédié quand d'autres agents travaillent.
3. État du code (à vérifier avant d'écrire, `android/README.md` fait foi) : en place = coquille Repas et `DriveActivity` (DRV-317), hôte WebView (DRV-312), agent embarqué et pont (DRV-313), pont natif `repasNative` et messages `drive.*` (DRV-314, DRV-320 ; voir § 3b), test automatique de débogage (DRV-318), émulateur, test de fumée et scénarios complets (DRV-319), aide d'installation côté front (DRV-316), **workflow de publication signée par étiquette `android-vX.Y.Z` et contrôle de l'APK (DRV-315, § 5.4)**. **Le cœur Kotlin sans Android `android/core` et les services de plateforme `IdentityProvider`, `LinkOpener` (AUTH-015, § 3c)** ; la connexion avec Google (AUTH-011, `IdentityProvider` côté Android) n'est pas encore écrite. **La mise à jour dans l'application (DRV-639, ADR 0009)** : `UpdateSource`, `ReleaseInfo`, `UpdateState`, `UpdateTransfer`, `UpdateFlow` dans le cœur, `app/src/direct` pour Android ; deux variantes de distribution (`direct` publiée, `play` à venir sans la permission ni ce code) ; voir § 3d.

## 3. Règles du domaine : WebView et pont sécurisés

- **Origines** (DRV-706 : par enseigne, `RetailerSite` dans le registre `RetailerSites`, le seul endroit du cœur qui nomme une enseigne ; navigation et pont sont deux listes : on peut naviguer sur plusieurs hôtes d'une enseigne sans que le pont ni l'agent existent sur la page du mot de passe ; un plan n'est livré qu'à une page de son enseigne, `RetailerSite.acceptsPlanOn`) : aujourd'hui navigation, injection et canal limités à `https://*.leclercdrive.fr` (`NavigationPolicy` refuse tout ce qui est ambigu : `@`, barre oblique inverse, port, point final, non-ASCII ; un autre site `http(s)` part dans le navigateur du téléphone, tout autre schéma est bloqué). Jamais `*`.
- **Écran du drive par enseigne** (DRV-707) : `DriveActivity` s'ouvre sur UNE enseigne (`site` : le passage en cours, sinon l'extra `retailer`, sinon l'enseigne d'avant ; `RetailerSites.forScreen`) et tout ce qu'il fait est de cette enseigne (navigation `decide(site, url)`, origines du pont et injection posées avant le premier chargement, mode du site `SiteMode`, mémoires, textes). **Un profil de WebView par enseigne** (`DriveProfileName` : `drive` reste celui de l'enseigne d'avant, ne jamais le renommer : ce serait déconnecter tout le monde ; `drive-<id>` pour les autres). **`strings.xml` ne nomme aucune enseigne** (`%1$s` nom, `%2$s` forme avec « de », `getString(id, site.name, site.nameDe)` ; `screen-retailer.spec.ts` compare le rendu pour Leclerc au texte d'avant). `app.info` annonce `retailers` (champ facultatif, une capacité, jamais un numéro de version) ; `drive.setup` accepte un `retailer` facultatif. L'enseigne FICTIVE d'essai (`*.exemple-b.test`) n'existe que dans `app/src/debug` (`TestRetailers`, vide dans `app/src/release`) et sert au scénario 19 de `make android-e2e` ; la WebView de l'émulateur (113) n'a pas `MULTI_PROFILE` : les profils se vérifient sur un téléphone récent. Lancer `make android-e2e` seulement sous `flock /tmp/repas-android-e2e.lock` (un seul émulateur partagé), depuis le dépôt dont les dossiers sont montés dans le conteneur.
- **Pas de `addJavascriptInterface`.** Un seul canal : `WebViewCompat.addWebMessageListener` (nom `repasHost`, mêmes origines), messages **texte JSON de 64 Ko au plus** dans les deux sens, forme vérifiée par `BridgeMessages` qui ignore (en ne journalisant que la **raison**, jamais le contenu) toute origine, cadre secondaire, non-texte, taille, JSON ou type hors protocole. Même règle pour le futur `repasNative` : **une seule origine** autorisée (celle du front Repas, constante de construction), bornes 64 Ko, refus de toute autre forme.
- **Injection** : `addDocumentStartJavaScript` (repli `evaluateJavascript` après `onPageFinished`, mêmes pages), page principale seulement (le défi anti-robot est un cadre d'un autre site : pas d'agent), une fois. L'agent est un **actif de l'APK** vérifié à la construction et **revérifié au démarrage** (`AgentAsset`) ; altéré ou absent, il n'est jamais injecté. Jamais de code reçu d'un site. Une fois l'agent démarré (il lit `window.repasHost` une seule fois), `injection.js` retire `repasHost` de la page : propriété vide et non reconfigurable, retirée aussi si l'agent échoue au démarrage ; le relais n'appelle aucune méthode de tableau. La page de test de l'émulateur ne voit donc plus le pont : elle ne rend compte que de ce que l'agent fait (`agent-ui`).
- **Mode ordinateur permanent** (`UserAgent.kt`, `DesktopMode.kt`) : agent utilisateur Linux de bureau sans `wv`, sans `Mobile`, sans `Android` (`Chrome/<majeur>.0.0.0`), indications client cohérentes (plateforme Linux, mobile faux, « Android WebView » renommé « Google Chrome », facteur de forme bureau), fenêtre large et zoom au pincement. Sans cela Leclerc sert son site mobile (`m-courses`) dont les routes sont inconnues. Chaque faiblesse est notée au journal (sans adresse ni contenu) et l'application continue ; sans version de Chrome lisible, l'identité de la WebView reste en place.
- **Page de départ d'un plan** : `DrivePlan.startUrl` = `NavigationPolicy.START_URL`, l'**accueil de l'enseigne** (`https://www.leclercdrive.fr/`), comme `SetupRequest.startUrl` et « Ouvrir le drive Leclerc » du menu, quel que soit l'hôte du magasin du plan. Constat de la recette réelle du 2026-10-18 (Pixel 9, application 0.1.3) : `https://<hôte>/magasin-<id>-<id>/` (ce qu'ouvrait la PR #125) **et la racine de l'hôte du magasin `https://<hôte>/`** (ce qu'ouvrait la PR #128, d'après l'hypothèse de DRV-319 que le faux site confirmait à tort) sont des **pages 404** du vrai site ; l'accueil de l'enseigne, session ouverte, montre l'accueil du magasin de l'utilisateur et son bouton « Commencer mes courses », qui mène aux vraies pages (`https://<hôte>/magasin-<id>-<id>-<Ville>/…`, celles que lisent `NavigationPolicy.isStorePage` et l'agent). L'accueil n'est pas une page de magasin pour l'agent : il attend, `StoreBanner.OPEN` dit « Ouvre ton magasin… touche « Commencer mes courses » », **l'application ne clique jamais à la place de l'utilisateur**, et le plan part tout seul dès qu'une page de magasin est atteinte (`STORE_MISMATCH` si ce n'est pas le bon). **Repli (ticket E)** : si le site refuse la page (statut 4xx/5xx), tarde (25 s) ou la sert sans agent (10 s), `OpeningWatch` le dit (`PageTrouble`) et `StoreBanner.PLAN` montre « Cette page n'est pas celle de ton magasin… » avec le bouton « Ouvrir l'accueil du drive » (recharge `PassRequest.startUrl`, donc l'accueil de l'enseigne, jamais une page 404). 403 et 429 (défi de l'anti-robot) laissent la page visible. Une page « introuvable » servie avec le statut 200 n'est pas vue (l'application ne lit pas les pages) : à confirmer sur le vrai site. Le plan ne part jamais vers une page refusée. **L'ordre des événements d'une page n'est pas garanti** (`onReceivedHttpError` précède `onPageStarted`). Garde : `OpeningWatchTest`, `StoreBannerTest`, `DrivePlanTest`, `NavigationPolicyTest`, scénarios 2 et 8 à 12 de `make android-e2e` (le scénario 2 échoue si le départ retombe sur la racine de l'hôte du magasin).
- **Zoom de la page : un geste de l'utilisateur, jamais un réglage.** Fenêtre large et vue d'ensemble (`useWideViewPort`, `loadWithOverviewMode`), pincement et double toucher, plus les entrées « Agrandir la page » / « Réduire la page » du menu du drive (`zoomBy`, ×1,5). Pas de `textZoom`, de `TEXT_AUTOSIZING` ni de `setInitialScale` : ils changeraient le texte de l'interface de l'agent et refont la mise en page d'un site que l'on ne peut pas ouvrir (décision et raisons : `android/README.md`, « La lisibilité en mode ordinateur »). L'interface de l'agent lit le zoom à chaque instant (`drive-agent/src/ui/scale.ts`) : elle reste lisible (facteur 2,38 sur un Pixel 9) quel que soit le zoom de la page.
- **Écrans** : `android:taskAffinity=""` sur les deux activités (le manifeste et `shell.spec.ts` le gardent) ; `DriveActivity` masque son contenu dans les captures d'écran et l'aperçu des applications récentes, sauf dans l'APK de débogage (`shell.spec.ts`).
- **Réglages** : JavaScript et stockage du DOM actifs, `allowFileAccess`/`allowContentAccess` faux, contenu mixte refusé, `safeBrowsingEnabled`, `usesCleartextTraffic` faux, `allowBackup` faux. Les cookies tiers sont acceptés pour la WebView (anti-robot) : ne rien changer aux cookies sans essai sur téléphone.
- **Cookies et session** : l'utilisateur se connecte **lui-même** ; cookies conservés entre deux ouvertures, jamais lus ni journalisés, exclus de toute sauvegarde ou transfert (`res/xml/data_extraction_rules.xml`) ; « Se déconnecter de Leclerc » (`clearBrowserData` ; la fenêtre de confirmation détaille ce qui est effacé) efface cookies, stockage du site, cache et historique.
- **Une seule permission : Internet** (pas même `ACCESS_NETWORK_STATE`). Toute autre permission est refusée, **sauf `REQUEST_INSTALL_PACKAGES`, déclarée dans `app/src/direct` seulement** (DRV-639 : l'application ouvre l'installateur d'Android pour se mettre à jour ; ni dans le manifeste commun, ni dans la variante `play`, ni dans un APK de débogage : `build.sh test` et `shell.spec.ts`/`update.spec.ts` le vérifient).
- **Écran allumé** : `FLAG_KEEP_SCREEN_ON` au premier plan aujourd'hui ; DRV-314 le restreindra à la durée d'un passage.
- **`targetSdk` 36** : affichage bord à bord obligatoire, marges sous les barres, l'encoche et le clavier par `setOnApplyWindowInsetsListener`; geste « retour » par `OnBackInvokedCallback` (`android:enableOnBackInvokedCallback="true"`), jamais `onBackPressed`. `configChanges` évite que la rotation recharge la page.
- **Variante de débogage ≠ production** : les menus « Test automatique (débogage) » et « Plan d'essai (débogage) » n'existent que sous `BuildConfig.DEBUG` ; `AgentAsset.assemble` remplace le marqueur `/*__DEBUG__*/false` par `true` **seulement** en débogage (l'agent n'honore `selftest` que si la page a annoncé `debug: true`) ; `debug-plan.json` n'est que dans l'APK de débogage. Ne jamais livrer un APK de production avec l'un d'eux.
- **Signature** : aucune clé, mot de passe ni secret dans le dépôt (public ; `hygiene.spec.ts` le vérifie, seule `android/debug.keystore` est suivie). La clé de publication arrive par **quatre variables d'environnement** : `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` (décodée dans un fichier temporaire du conteneur, effacé en sortie, jamais affichée), plus `ANDROID_VERSION_TAG` : le **nom ET le code** de version d'une publication en sont tirés (`android-v1.2.3` donne `1.2.3` et 1 002 003, donc le code ne baisse jamais tant que les étiquettes montent) ; `ANDROID_VERSION_CODE` ne sert qu'aux constructions de débogage de la CI (numéro d'exécution) et, donné avec une publication, doit être égal au code de l'étiquette. Une valeur de version présente mais invalide est refusée. Débogage et publication n'ont pas la même clé : désinstaller avant de passer de l'un à l'autre.

## 3b. Contrat du pont natif `repasNative` (côté front fait, côté Android à écrire)

Lire `src/features/drive/bridge/native.ts` et `driveBridge.ts` du front : l'application doit s'y conformer, pas l'inverse. Un objet `repasNative` (`addWebMessageListener`, **origine du front Repas seulement**, constante de construction `REPAS_ORIGIN`, jamais `*`) avec `postMessage(texte)` et des événements `message` dont `data` est du **texte JSON `{"v":1,…}` de 64 Ko au plus** (octets UTF-8). Page vers application : `app.info`, `drive.start` (`plan` = message `plan` du protocole v1), `drive.cancel`. Application vers page : `app.info` (`version`, `versionCode` entier, `drive` booléen : agent intact et WebView assez récente), `drive.result` (`result` = message `result` ou `setup-result` valide), `drive.error` (`code` en majuscules `^[A-Z][A-Z0-9_]{0,63}$`, `runId` uuid ou nul), `error` (`code`, pour un message refusé : par exemple `UNKNOWN_TYPE`). Règles à tenir côté Kotlin : un seul passage à la fois ; le résultat est mis en file si la page s'est rechargée ; la WebView du front ne reçoit **jamais** l'agent ni les cookies de Leclerc (deux WebView séparées, `DriveActivity` pour le drive) ; hôtes du drive autorisés écrits en dur (un plan d’un autre hôte, ou de plus de 64 Ko, est refusé) ; reprise 24 h après interruption (identifiant d'exécution et plan, aucun cookie).

## 3c. Le cœur sans Android et l'application (AUTH-015)

Page de référence : `android/ARCHITECTURE.md`. Décision D5 de l'ADR 0024 du back : pouvoir sortir sur iPhone un jour sans tout réécrire ; aucun code iOS, pas de Kotlin Multiplatform aujourd'hui, seulement un terrain rangé.

- **Règle d'or : le cœur n'importe rien d'Android.** `android/core` est un module Kotlin JVM sans plugin Android ni SDK : ni `android.*`, ni `androidx.*`, ni `BuildConfig`, ni `R`, ni une classe d'activité. Un `import android.…` n'y compile pas (« Unresolved reference ») ; `CoreArchitectureTest` (`make android-test`) et `android/__tests__/core.spec.ts` (`make check`) échouent d'un message clair. `app` dépend de `core` (`implementation(project(":core"))`), jamais l'inverse.
- **Où mettre un code** : une règle qui se joue sans téléphone, sans WebView et sans `Context` va **dans le cœur**, avec ses tests JUnit ; la colle d'Android (WebView, vue, activité, manifeste) reste dans `app`, aussi mince que possible (le cœur décide, l'application exécute) ; quand le cœur a besoin de la plateforme, **il écrit l'interface** (sans type Android dans ses signatures) et **l'application l'implémente** (`AndroidServices.kt`).
- **Les interfaces de plateforme** : `IdentityProvider` (`signIn(clientId, nonce, callback)` : jeton d'identité ; contrat dans sa documentation : un seul rappel, jamais après `cancel()`, rien au journal ; `IdentityResult.Token.toString()` ne montre pas le jeton), `LinkOpener` (`open(url)`), et les trois stockages `PassStore`, `StorePathStore` et `FinalizeOutcomeStore`. Pas de `SecureStore` : rien ne garde de secret. Le pont de connexion Google (AUTH-011) s'écrit contre `IdentityProvider`, sans toucher à la WebView.
- **Les emprunts à la JVM sont une liste fermée** (`CoreRules.BORROWED_FROM_THE_JVM` : `org.json`, `MessageDigest`, `Base64`, `Normalizer`, `Locale`) : c'est ce qu'un module Kotlin Multiplatform devrait remplacer (`ARCHITECTURE.md`, « Ce que Kotlin Multiplatform demandera »). En ajouter un, c'est l'ajouter à cette liste **et** à `ARCHITECTURE.md`, en le sachant.
- **Ce qui reste dans `app/src/test`** : les tests qui touchent Android (`LoadProblemTest` rapproche les codes d'erreur des constantes de la WebView) ou un actif de l'application (`InjectionAssetTest`, `DebugRunTest`, `BuildOriginTest`). Tout le reste est dans `core/src/test`, avec `src/test/resources` (copies des exemples du protocole que `android/__tests__/` relit).
- **`android/ARCHITECTURE.md` nomme chaque fichier Kotlin** (`core.spec.ts` le vérifie) : un fichier ajouté, déplacé ou supprimé s'y inscrit dans la même PR, dans la partie du cœur ou de l'application.

## 3d. La mise à jour dans l'application (DRV-639)

Pages de référence : `android/README.md` (« La mise à jour dans l'application »), `android/PUBLICATION.md` (adresses, essai sur téléphone), `docs/adr/0009-mise-a-jour-de-l-application.md`.

- **Adresses en dur, à un seul endroit** : `UpdateSource.kt` (le `version.json` de la release roulante `android-latest` ; `releases/latest/download/` ne mène PAS à l'application). Jamais une adresse venue d'un message du pont, de la page ou de `version.json` (`apkUrl` est ignoré : l'APK est calculé du nom de version validé). Chaque redirection est jugée (`isTrustedRedirect`, trois hôtes exacts, `https`). `GitHub` n'est nommé que dans ce fichier (`android/__tests__/update.spec.ts`).
- **Règles pures dans le cœur, colle dans `app/src/direct`** : `UpdateFlow` (ports `UpdateStorage`, `UpdatePlatform`, `HttpHop` via `SafeFetcher`) se teste avec de faux serveurs (`UpdateFakes.kt`) : mauvaise empreinte, taille, redirection hors liste, annulation, coupure, effacement dans tous les cas. Le fichier est effacé après toute erreur, après l'installateur (`onActivityResult`) et au démarrage de la coquille (jamais de `RepasApp.onCreate` : le fournisseur de fichiers peut démarrer le processus pendant l'installation).
- **Variantes** : tout ce qui installe va dans `app/src/direct`, jamais dans `src/main` ; `src/main` ne connaît que l'interface `SelfUpdate`. Un code de mise à jour dans `src/play` ou la permission dans le manifeste commun fait échouer `build.sh test`. Un APK de débogage ne se met jamais à jour.
- **Signature** : ne jamais utiliser `PackageInstaller`, un téléchargement dans « Téléchargements » (`DownloadManager`), `file://`, un flag qui assouplit la vérification ; l'installateur d'Android juge la clé.
- **Ne se prouve sur téléphone qu'avec deux versions publiées** (clé de publication) : procédure dans `PUBLICATION.md`. Le test de fumée vérifie seulement que le débogage ne l'offre pas.

## 4. Émulateur Docker permanent et test de fumée

- **Jamais Leclerc** : le DNS de l'émulateur (`dnsmasq`) envoie `*.leclercdrive.fr` vers un faux site HTTPS local (`10.0.2.2`, `testsite.py`) et ne résout **rien d'autre** ; `make android-smoke` s'arrête avant d'ouvrir quoi que ce soit si ce nom ne pointe pas vers `10.0.2.2`, et le journal du DNS prouve qu'aucune demande n'est partie. Seul le premier lancement va sur Internet (SDK chez Google). Certificat jetable dans le volume, accepté par la WebView par `--ignore-certificate-errors-spki-list` écrit dans l'émulateur seulement (image Google APIs « userdebug », pas Play Store) : l'application n'est pas modifiée.
- **KVM** (`/dev/kvm`) : sans lui l'émulateur est inutilisable et les commandes refusent de démarrer (code 3). Sous WSL2, **étape humaine** : `sudo modprobe kvm_intel && sudo chmod 666 /dev/kvm` (`kvm_amd` sur AMD), à refaire à chaque redémarrage de WSL, ou une fois pour toutes dans `/etc/wsl.conf` (`[boot]` → `command = modprobe kvm_intel && chmod 666 /dev/kvm`, sans écraser un `[boot]` existant) puis `wsl --shutdown` côté Windows. C’est une étape humaine (système de l’utilisateur, droits `sudo`) : l’agent la demande en une étape à la fois, au lieu de la faire.
- **Écran d'un Pixel 9** : 1080 × 2424 à 420 dpi (411 × 923 dp), réécrit à chaque démarrage (`EMULATOR_LCD_*`). Un écran plus petit cacherait le défaut du site en mode ordinateur ; les faux sites n'ont **pas** de balise `viewport` (sinon fenêtre de 411 px et rien à compenser). `make android-e2e` mesure en dp les cibles de l'agent (`touch_target`, 44 dp au moins) et le facteur de son interface (`display_measures`) : lire `e04` et `e05`.
- **Permanent** : SDK, image système (Android 14 Google APIs x86_64) et AVD `repas` dans le volume Docker `repas-front_android-emulator-sdk` (≈ 2 Go téléchargés, 6 Go sur disque, 2 min 45 la première fois, ≈ 30 s ensuite). Profil Compose à part (`make stop` ne l'arrête pas). Réglages : `EMULATOR_MEMORY` (3072 Mo), `EMULATOR_CORES` (4). Pour repartir de zéro : `make android-emulator-down` puis `docker volume rm repas-front_android-emulator-sdk`.
- **Le verdict attendu du test de fumée est « KO avec `Arrêt : UNSUPPORTED_PAGE` »** pour le test automatique : la page locale n'est pas une page de magasin ; ce qui compte est que le rapport arrive (26 contrôles OK). Exit 0 = tout passe, 1 = échec (voir `rapport.txt` et `journal-android.txt`), 3 = KVM manque.
- **Lire les captures avant de conclure** : `android/dist/smoke/01-page-locale.png`, `02-menu.png`, `03-diagnostic-agent.png`, `04-rapport-selftest.png` et `rapport.txt` ; un « OK » sans avoir regardé les images ne prouve rien.
- La CI n'a pas KVM : l'émulateur est une cible **manuelle**, `make check` n'y touche pas (il joue seulement `android/__tests__/emulator-e2e.spec.ts` : plans valides, scripts de syntaxe correcte, aucun faux certificat dans l'application).
- **`make android-e2e`** (DRV-319, partie 2) : le faux Leclerc complet (`drive-agent/fake-leclerc/`, Node 24 copié dans l'image de l'émulateur, dossier monté en lecture seule) tourne dans le conteneur sur `127.0.0.1:8099`, derrière le relais HTTPS de `testsite.py` pour le seul nom `courses-test.leclercdrive.fr` ; son pilotage `/__fake/*` (état, défauts, remise à neuf) n'est joignable que par `docker compose exec`. Le faux Repas (`repaspage.html`) reçoit les plans par `/__command` (`plan` complet, `android/emulator/e2e/*.json` avec `__RUN_ID__`) et relève chaque résultat (`detail` : `ingrédient:issue:référence:quantité`). Après un changement dans `android/emulator/`, `compose.yaml` ou `drive-agent/fake-leclerc/` : `make android-emulator-down` puis `up`. Le faux certificat n'est accepté que par la WebView de l'émulateur (`lib.sh`, `/data/local/tmp/webview-command-line`), jamais par l'application. **Lire les captures `e01` à `e13`** avant de conclure.

## 5. Recettes

### 5.1 Modifier l'application (Kotlin)
Mettre la règle dans une classe du **cœur** (`android/core`, Kotlin sans classe Android, § 3c) avec ses tests JUnit, la coller ensuite dans `MainActivity`/`AgentHost` (`app`) → `make android-test` → `make android` → `make android-smoke` si le pont, l'injection ou le menu changent → lire les captures. Tout ce qui touche `DesktopMode`/`MainActivity` ne se prouve que sur téléphone : le dire dans « À relire » (recette de l'utilisateur).

### 5.2 Le pont ou `injection.js` change
Garder la forme attendue par `drive-agent/src/transport/bridge.ts` (`postMessage(texte)` et `addEventListener('message', …)`), tester dans `android/__tests__/injection.spec.ts` (jsdom, agent réel, faux site), borner (64 Ko) et valider côté Kotlin **et** côté agent. Le message `hello` n'est pas du protocole.

### 5.3 L'agent a changé
`make agent-build` puis `make android-agent-hash`, commiter `android/agent.js.sha384`, le dire dans la PR (voir `repas-agent-dev`).

### 5.4 Publier (clé et secrets : étapes humaines, l'assistant ne les voit jamais ; étiquette et releases : l'assistant, phase bêta)
La dernière version est toujours à des adresses fixes, la release roulante `android-latest` (`releases/download/android-latest/{version.json,repas-drive.apk}` ; `releases/latest` est pris par les releases du site). Les sous-agents ne publient jamais : ils s'arrêtent à la PR verte. Garde-fous qui restent : jamais de secret dans le chat, `GOOGLE_CLIENT_ID` (et `DRIVE_ENABLED` côté back) allumés par l'humain, jamais de force-push. Tout est dans `android/PUBLICATION.md`, que l'assistant déroule **une étape à la fois** avec l'utilisateur (non devops) : 1. clé créée par l'utilisateur (`keytool` dans Docker, hors du dépôt, **deux copies** : la perdre empêche toute mise à jour par-dessus) ; 2. empreinte SHA-256 du certificat (publique, donnée dans le chat) ; 3. quatre secrets GitHub (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, posés par l'utilisateur avec `gh secret set` ou le site, jamais dans le chat) ; 4. **l'assistant** ouvre la PR de `public/.well-known/assetlinks.json` (empreinte de l'étape 2, un seul paquet `eu.kantin.repas.drive`, **jamais** l'empreinte de `debug.keystore`), puis l'assistant publie une version du site (`gh release create vX.Y.Z`, sans approbation depuis le 2026-10-20) : le workflow refuse de publier tant que le fichier manque, car il y lit l'empreinte attendue du certificat ; 5. **l'assistant principal** (depuis le 2026-10-20, phase bêta ; jamais un sous-agent) pousse `git tag android-vX.Y.Z && git push origin android-vX.Y.Z` (un sous-agent ne le fait jamais ; **si le protocole a changé** — champ ajouté au résultat, comme `stats` avec l'agent 0.15.0 — le site (release `vX.Y.Z`) est déployé AVANT cette étiquette : un récepteur qui ne connaît pas le champ rejette le message) ; `android-release.yml` construit, contrôle, publie (release ordinaire, `--latest=false`) ; 6. vérification (`sha256sum -c`), 7. installation sur le téléphone, 8. mise à jour par-dessus. À surveiller : la vérification d'identité des développeurs d'Android (hors Google Play). Les pré-versions `android-dev-<date>` (workflow `android.yml` lancé à la main) (et les anciennes `android-lab-<date>` du banc d'essai retiré, à supprimer) sont signées d'une clé **publique**, portent un avertissement dans leurs notes et ne vont **jamais** sur le téléphone des courses ; les étiquettes `vX.Y.Z` sont réservées à `release.yml`, `android-vX.Y.Z` à `android-release.yml`. Modifier le workflow : `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest` (aucune erreur), `make check` (`publication.spec.ts` garde le déclencheur unique, les droits, les secrets seulement dans des blocs `env`), `make android-release-selftest`, et un essai local avec une clé jetable (`make android-release`, `make android-release-verify`, `adb install` dans l'émulateur).

## 7. Erreurs fréquentes

- Oublier `make android-agent-hash` (la construction échoue) ; donner `ANDROID_VERSION_CODE` en publication (le code vient de l'étiquette, un compteur différent est refusé) ; pousser une étiquette plus basse que la dernière (refusé : plus de mise à jour par-dessus) ; publier avant `assetlinks.json` (le workflow refuse).
- Ajouter `addJavascriptInterface` « pour aller plus vite », ou un `*` dans les origines.
- Mettre dans `android/core` un `import android.…`, `BuildConfig` ou `R` « juste cette fois » : le cœur ne compile pas avec ; écrire plutôt une interface dans le cœur et l'implémenter dans `app`. Et l'inverse : ne pas rester dans `MainActivity` une règle qui se jouerait sans téléphone.
- Passer par `onBackPressed` (jamais appelé en `targetSdk` 36) ou oublier les marges (contenu sous les barres).
- Laisser une fonction de débogage hors `BuildConfig.DEBUG` ; mélanger APK de débogage et de publication sur le téléphone.
- Ouvrir le vrai Leclerc dans l'émulateur, ou conclure d'un test de fumée sans regarder les captures.
- Ouvrir un plan sur `/magasin-<id>-<id>/` ou sur la racine de l'hôte du magasin (deux pages 404 du vrai site), ou écrire un faux site qui les sert : il cache le défaut au lieu de l'attraper (le faux site les refuse, comme le vrai, et sert l'accueil sur `www.leclercdrive.fr`). Un faux site écrit d'après une hypothèse non mesurée valide cette hypothèse : le comparer aux constats de la recette réelle. Cliquer à la place de l'utilisateur sur « Commencer mes courses » : jamais.
- Envoyer le plan à une page que le site a refusée (statut ≥ 400) ou laisser un plan sans bandeau : l'utilisateur reste devant un écran muet. Toute nouvelle sortie « la page n'est pas bonne » passe par `PageTrouble` et un test d'`OpeningWatchTest` ; ne pas supposer que `onPageStarted` précède les autres événements d'une page.
- Écrire dans le journal Android une adresse, un cookie ou le contenu d'un message.

## 8. Interdits

Contacter Leclerc ; exposer un objet natif aux pages ; demander une permission autre qu'Internet (hors `REQUEST_INSTALL_PACKAGES` de la variante `direct`) ; mettre une clé, un mot de passe ou un secret dans le dépôt, une PR ou le chat ; créer une release de production (`vX.Y.Z`) ou pousser une étiquette `android-vX.Y.Z` (c'est l'utilisateur qui le fait) ; créer, lire ou modifier une vraie clé de signature ou les secrets GitHub (un essai se fait avec une clé jetable hors du dépôt) ; ajouter un déclencheur (PR, `main`, `workflow_dispatch`) ou une variante sans clé à `android-release.yml` ; `--no-verify`, force-push, push sur `main` ; fusionner une PR dont un contrôle n'est pas vert.

## Ajouter une enseigne (DRV-711, sensible : effort xhigh)

Plan : `docs/drive/multi-enseignes.md` § 3.5 (dépôt back) ; `android/ARCHITECTURE.md`, « Plusieurs enseignes » ; consignes : `docs/drive/consignes-agents.md`. **Ce que tu ajoutes** : UNE entrée `RetailerSite` dans `RetailerSites` (`android/core`, le seul endroit du cœur qui nomme une enseigne : identifiant, noms, accueil, hôtes de navigation et hôtes où le pont existe, mode du site `SiteMode`, règle d'adresse du magasin), sans autre fichier à nommer ; le profil de WebView (`DriveProfileName`), les mémoires par enseigne (`RetailerValue`) et l'annonce `app.info.retailers` en découlent. **Sécurité** : les hôtes où le pont `repasHost` et l'agent existent sont une liste **à part et plus courte** que celle de la navigation (jamais la page du mot de passe de l'enseigne), jamais un joker commun ; un plan n'est livré qu'à une page de son enseigne ; une adresse n'est celle que d'une seule enseigne. **Tests** : le cœur sans téléphone (`make android-test`), la concordance avec `retailers.sample.json`, l'enseigne d'essai fictive de la variante de débogage, le scénario de bout en bout (`make android-e2e`, à lancer par l'assistant, pas par un sous-agent). **Ce que tu ne fais pas** : durcir Leclerc (aucun littéral d'hôte ni `"leclerc"` hors du registre), déduire les hôtes d'une enseigne de ceux d'une autre, nommer une enseigne dans `strings.xml` (`%1$s` le nom, `%2$s` la forme avec « de »), allumer l'enseigne ni publier (`android-vX.Y.Z` est une étiquette de l'assistant principal).
