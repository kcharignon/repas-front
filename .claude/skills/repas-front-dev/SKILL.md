# repas-front-dev — développer le front Repas

Vue 3 (`<script setup>`), TypeScript strict, Vite, Pinia, TanStack Query, client OpenAPI généré, Tailwind + Reka UI, Vitest, Playwright. **Tout tourne dans Docker** (pas de Node sur l'hôte) : passer par `make`.

## 0. Avant toute chose

1. Lire `CLAUDE.md` du front, `docs/adr/README.md` (ADR 0002 contrat, 0003 design, 0005 session, 0006 PWA) et, pour le chantier drive, le ticket `docs/drive/tickets/DRV-4xx-*.md` **du dépôt back** `kcharignon/repas` (autonome ; ses sections « RÉVISION », « Précisions du back » et « Réalisation » priment sur le texte d'origine), `docs/drive/README.md`, `docs/drive/architecture.md` §§ 7-9 et `docs/drive/consignes-agents.md`.
2. Règles transverses (détail : `consignes-agents.md` du back) : aucun contact avec Leclerc, aucune donnée réelle (valeurs factices `123456`, `Ville-Test`), jamais de déploiement, de release ni de secret ; une PR n'est fusionnée que si **tous** les contrôles de la CI sont verts ; commits courts en français **sans `Co-Authored-By`** ; travailler dans un worktree dédié quand d'autres agents travaillent (`git worktree add`), jamais dans le répertoire d'un autre agent (et pour Docker, dans **la même commande** : `COMPOSE_PROJECT_NAME=repas-front-<nom> FRONT_PORT=<port libre> make …`, sinon le projet `repas-front` du répertoire principal, ses volumes et son port 5173 sont réutilisés ; `make install` une fois, `make stop` et la suppression du volume `<projet>_node_modules` à la fin) ; ne toucher ni au dépôt back ni à sa roadmap : dire dans le rapport ce qu'il faut cocher.
3. Un module décrit par un ticket n'existe peut-être pas encore : vérifier dans `src/` avant de l'utiliser (`git log`, `src/features/drive/`). Les écrans DRV-403, 404, 405, 410, 316, 504 et 612 et le pont (DRV-402) existent ; la carte du code ci-dessous les situe.

## 2. Conventions

- **Types de l'API générés, jamais écrits à la main** (`src/api/schema.d.ts`, commité mais produit par `openapi-typescript`) : un changement de contrat doit casser la compilation. Appels par `unwrap(api.GET('/api/v1/drive/settings'))` avec `useSessionStore().api` ; données serveur par TanStack Query (`queries.ts` par feature, clés exportées comme `driveKeys`).
- **Aucune logique métier dans un composant** : les conditionnements (`packs`, `packsStatus`) viennent du plan du back ; le front affiche, saisit, appelle, relit. Une écriture sur liste porte `If-Match` (`ifMatch(list.version)`) ; `412`/`409`/`DRIVE_DISABLED` = la ressource a changé : l'écran se relit (`isStale` de `src/notifications/failures.ts`).
- **Erreurs du back** : le message est un code en majuscules (`SHOPPING_LIST_SENT`, `DRIVE_NOT_CONFIGURED`, `DRIVE_STORE_MISMATCH`, `DRIVE_CHOICE_INVALID`…). Un code que l'écran doit distinguer reçoit son texte dans `driveCodes` (`failures.ts`) et `errors.*` de `fr.ts` (aujourd’hui `DRIVE_DISABLED`, `DRIVE_NOT_CONFIGURED`, `DRIVE_STORE_MISMATCH`, `DRIVE_CHOICE_INVALID`, `DRIVE_CHOICE_NOT_FOUND`, `DRIVE_LIMIT_REACHED` (plafonds par utilisateur : 1 000 préférences par magasin, 5 000 écritures de produits par jour, `422` sur `PUT /drive/choices` et `PUT /drive/choices/{slug}`), `DRIVE_RATE_LIMITED` (limiteur de débit, `429`, voir « Limiteur de débit » plus bas), `DRIVE_STORE_INVALID`, `SHOPPING_LIST_SENT`, `_NOT_SENT`, `_NOT_SENDABLE`, `_EMPTY`, et pour l'administration des unités (DRV-409) `UNIT_MEASURE_INCOMPLETE` et `UNIT_BASE_FACTOR_INVALID`) ; un code absent retombe sur le texte du statut.
- **Textes** : jamais de chaîne en dur dans un composant, tout dans `src/i18n/fr.ts` (français seul, tutoiement partout : « tu », « ton », « ouvre » ; jamais « vous » ni « ouvrez », le test de voix échoue). Une clé manquante fait un `console.warn`, donc **échoue le test** (`src/__tests__/setup.ts` : aucun `console.warn`/`console.error` toléré).
- **Couleurs par jetons** : `src/design/theme.css` (clair et sombre) et classes Tailwind de jeton (`bg-primary`, `text-muted`, `bg-soft`…) ; jamais d'hexadécimal dans un composant. Composants `Ui*` de `src/design/`, catalogue sur `/design`.
- **Session** (ADR 0005) : jeton d'accès **en mémoire** (store Pinia), jamais dans `localStorage`/`sessionStorage`/cookie lisible ; refresh par cookie `HttpOnly`. Seul un indice booléen (`repas.session`) et un instantané utilisateur vivent en `localStorage`. Seul un `401` du rafraîchissement met fin à la session (`429`, `5xx`, réseau : elle reste, délai d'attente avant de redemander) ; `clear()` efface aussi le brouillon du drive et le store `driveReturn` (`src/session/accountData.ts`) ; les autres onglets suivent par l'événement `storage` (`src/session/crossTab.ts`).
- **CSP de production** (`docker/Caddyfile`) : `default-src 'self'; script-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'`. **Aucune image externe** (pas de vignettes Leclerc en v1), pas de script en ligne, pas de nom de domaine ni de secret dans l'image : ne rien relâcher sans ADR.
- **Accessibilité et mobile** : WCAG AA, cibles tactiles ≥ 44 px, clavier, thèmes clair/sombre, `prefers-reduced-motion`. Le téléphone (Pixel 7) est la cible principale du drive.
- **Hors ligne** (ADR 0006) : le service worker ne met **aucune réponse de `/api` en cache** ; seule la liste en cours est relue depuis `localStorage` (`repas.cache`, au nom de l'utilisateur). Une action du drive (`send`, `reopen`, ouvrir le drive) est désactivée sans réseau, avec une explication.

## 3. Le drive côté front

- **Protocole partagé** : `import { encodeMessage, decodeMessage, validatePlan, validateResult, PROTOCOL_VERSION } from '@drive-protocol'` (alias vers `drive-agent/protocol/index.ts`, déclaré dans `vite.config.ts` et `tsconfig.app.json`). Ne jamais recopier un type, une borne ou un schéma : importer. Tout résultat reçu passe par `validateResult` avant d'être affiché ou enregistré ; les libellés s'affichent en texte (jamais `v-html`). Bornes : 64 Ko, 100 lignes, 5 produits, 20 refusés.
- **Plan** : `GET /api/v1/drive/plans/{id}` → `buildPlanMessage` (DRV-404) traduit `retailerProductId` en `id`, garde l'ordre de priorité, **recopie `needed`**, applique les surcharges (`replace` : `KNOWN` devient `NEW` avec `replaces` ; `skip` : `SKIP`). Le plan se recharge à chaque ouverture de l'écran.
- **Pont natif `repasNative`** (décision D28). Côté front, c'est fait (`src/features/drive/bridge/`, importer **uniquement** `@/features/drive/bridge`, jamais `window.repasNative` dans un écran) : `driveBridge.isAvailable()`, `info()` (`app.info` → `{version, versionCode, drive}`, 3 s de délai), `startRun(plan, listId)` (valide le plan par `validatePlan`, écrit le brouillon **avant** d'envoyer `drive.start`), `cancel()` (`drive.cancel`), `listen()` à appeler au démarrage, `onEvent` (`result`, `stale`, `refused`, `invalid` ; les événements arrivés sans écran sont rejoués au premier abonné), `loadDraft`/`clearDraft`/`matchesDraft`. Erreurs `DriveBridgeError` (`UNAVAILABLE`, `INVALID_PLAN`, `TOO_LARGE` > 64 Ko, `RUN_IN_PROGRESS`, `SEND_FAILED`, `REFUSED`, `TIMEOUT`, `INVALID_RESPONSE`) : l'écran choisit le texte, le message n'est jamais journalisé ni affiché. Hors application (`UNAVAILABLE`) : proposer d'installer l'application (DRV-316) et le mode assisté ; **dans** l'application, jamais « installer » : l'entrée de « Moi » (`AppHelpLink.vue`) et le bouton d'aide des réglages disent « Mettre à jour l'application » et mènent à `/drive/aide#mise-a-jour`, le titre de l'aide devient « L'application Repas ». **Côté Android le pont n'existe pas encore** (DRV-317 et DRV-314) : les tests jouent un faux canal (`bridge/__tests__/fakeNative.ts`). Plus de lien `repasdrive://`, plus de fragment d'adresse, plus de favori.
- **Brouillon de passage** `{runId, listId, retailer, startedAt, lines?}` (`retailer` : DRV-710, absent d'un ancien brouillon = le drive d'avant) dans `localStorage` (clé `repas.drive.run`, `DRAFT_TTL_MS` 24 h, validé à la lecture ; `lines` = pour chaque ligne du plan envoyé le slug, le statut envoyé et les identifiants des produits, écrites par `startRun` ; ni magasin, ni jeton, ni libellé ; repli en mémoire si `localStorage` est refusé : alors il ne survit pas) : l'utilisateur quitte l'écran pour le drive et le **service worker de production recharge la page** dès qu'il détecte une nouvelle version (`src/pwaUpdate.ts`). Le brouillon s'écrit **avant** de lancer le drive et se retrouve après rechargement ; un résultat dont le `runId` n'est pas celui du brouillon est ignoré (message). Toute écriture dans `localStorage` est protégée par `try/catch` (déjà fait dans `draft.ts` : réutiliser, ne pas réécrire).
- **Recoupement du résultat avec le plan** (DRV-614, revue C1 : la page de l'enseigne partage le monde JavaScript de l'agent et peut poster un faux résultat) : `restrictToPlan.ts` ne retient que les lignes que le plan envoyé explique (slug présent ; `ADDED` : produit du plan ; `CHOSEN` : ligne envoyée « à choisir », ou connue sans aucun produit disponible, ou remplacée ; `HAVE_AT_HOME` : pas pour une ligne passée) ; `returnStore` le fait à la réception avec `draft.lines`, sinon l'écran relit `GET /drive/plans/{id}` (`expectedFromPlan`, plus indulgent : il ne sait pas ce que l'utilisateur a remplacé) ; sans plan, rien n'est enregistré et « Réessayer l'enregistrement » relit le plan. Les lignes ignorées ne sont ni enregistrées ni affichées, seulement comptées (« N lignes inattendues ignorées »). Toute nouvelle issue de ligne de l'agent doit être ajoutée à `isExpected`.
- **Enregistrement des choix** (DRV-405) : un seul `PUT /drive/choices` (≤ 200 intentions) ; le cochage des articles au panier (DRV-747) est une écriture À PART, qui n'attend pas celle-ci. `CHOSEN` PRIMARY/FALLBACK → `ADD_PRODUCT` ; `ONCE` → rien ; chaque `rejected` → `REJECT_PRODUCT` ; `HAVE_AT_HOME` **après** les `REJECT_PRODUCT` du même ingrédient ; une ligne `ADDED` avec `price` → `REFRESH_PRICE` ; un produit jamais à la fois ajouté et refusé. En cas d'échec, garder le résultat en mémoire et proposer « Réessayer l'enregistrement » ; le brouillon ne s'efface qu'après succès.
- **Liste `SENT`** : lecture seule (pas de case, de `+`/`-`, de portions, de renommage), actions « Reprendre l'envoi », « Terminer », « Rouvrir la liste » (confirmation : « Le panier Leclerc ne sera pas vidé. »), « Supprimer ». `/liste` ne crée jamais de liste tout seul quand il n'y a que des `SENT`. `checked` n'est jamais modifié par un envoi lui-même ; seule l'écriture du passage (DRV-747, `POST /drive/plans/{id}/basket-lines`, `useMarkBasketLines`) coche les articles RÉELLEMENT mis au panier (`ADDED` et `CHOSEN` sans `notInCart` du résultat recoupé avec le plan, une fois, jamais bloquante), et la barre « N sur M articles dans le panier » s'affiche aussi sur une liste envoyée. Les lignes cochées ne partent pas : le plan et l'estimation du back ne les contiennent plus, `canSend` et « Reprendre l'envoi » comptent les articles non cochés, un plan sans ligne dit « Tous tes articles sont cochés. ». `DriveSendView` n'utilise qu'un plan lu après son ouverture ; le récapitulatif garde son plan lu au montage et n'invalide jamais le plan. Le bouton « Envoyer au drive » n'apparaît que si `GET /drive/settings` renvoie `enabled: true` ; « Rouvrir la liste » reste proposé interrupteur coupé (`POST /shopping-lists/{id}/reopen` répond `204`, DRV-613 : une liste figée par un retour arrière doit pouvoir être rouverte). L'écran « Reprendre l'envoi » (`DriveSendView.vue`) aussi : quand le plan répond `404 DRIVE_DISABLED` il dit « pas disponible » et, si la liste (`GET /shopping-lists/{id}`, lue alors seulement) est `SENT`, propose « Rouvrir la liste » avec la confirmation de l'écran de la liste, sans « Ouvrir le drive » ni « Envoyer au drive ».
- **Limiteur de débit (DRV-615)** : `429 DRIVE_RATE_LIMITED` sur `PUT /drive/settings`, `PUT /drive/choices`, `PUT`/`DELETE /drive/choices/{slug}` (60 par minute et par utilisateur) et `GET /drive/plans/{id}`, `GET /drive/estimates/{id}` (120 par minute). `Retry-After` est un **minimum** et il est optimiste (souvent 1 s) : `messageForFailure` dit toujours « au moins une minute » (`errors.driveRateLimited` / `driveWait`), jamais un compte à rebours en secondes. C'est un refus passager, distinct de `DRIVE_LIMIT_REACHED` : `isRateLimited(error)` (`failures.ts`) le reconnaît, il ne demande pas de relire l'écran (`isStale` reste faux). **Jamais de réessai tout seul** : `createQueryClient` ne relit pas au retour du focus ou du réseau une lecture dont la dernière erreur est un `429` ; seul le bouton « Réessayer » renvoie la requête. À l'enregistrement des choix (`DriveReturnView`), un `429` garde le résultat en mémoire, le lot et le brouillon, et le dit (`driveReturn.save.rateLimited`) : « Réessayer l'enregistrement » renvoie le même lot. Tests : `rateLimited(retryAfter)` de `src/__tests__/helpers.ts`, `fakeBack(page, { choices, plan, estimate })` de `e2e/support/drive.ts` (nombre de `429` avant de répondre), `e2e/drive-rate-limit.spec.ts`.
- **Libellé du magasin** : l'agent ne lit pas le libellé ; afficher « Magasin …123 » (derniers chiffres) et laisser nommer le magasin (champ facultatif de `PUT /drive/settings`).

## 4. Recettes

### 4.1 Nouvel écran ou nouvelle feature
1. Contrat à jour : `make api-update ref=<sha du back fusionné>`, relire le diff (un champ ajouté est compatible, un champ retiré est une rupture).
2. `src/features/<feature>/queries.ts` (clés, `useQuery`/`useMutation`, invalidations), vue + composants, route dans `src/router` (protégée par défaut ; `meta.public` seulement pour une page publique), textes dans `fr.ts`, composants `Ui*`.
3. Tests Vitest à côté (`__tests__/`) avec `stubApi` et `appContext()` de `src/__tests__/helpers.ts` : un appel d'API non prévu fait échouer le test. Cas : chargement, vide, succès, chaque code d'erreur du back, hors ligne.
   Un test qui ne touche ni au DOM ni à un composant `.vue` (logique pure, agent du drive) porte `// @vitest-environment node` en première ligne (jsdom coûte environ 0,5 s par fichier). Il ne doit importer aucun `.vue`, même par le routeur : en `node` Vitest compile les composants pour le rendu serveur et fausse la couverture.
4. e2e : faux back par `page.route` (modèle `e2e/shopping-list-sent.spec.ts`, indice de session posé par `addInitScript`), axe (`@axe-core/playwright`) sans violation A/AA. **Un test n'est joué qu'une fois, sur le téléphone** (projet `mobile`, Pixel 7) ; `{ tag: BUREAU }` (de `e2e/support/test.ts`) l'envoie AUSSI sur le bureau (projet `chromium`) quand la mise en page du bureau change ce qu'il vérifie, `{ tag: BUREAU_SEUL }` ou `{ tag: viewportTag(size) }` SEULEMENT sur le bureau (le test fixe lui-même une largeur de bureau) : voir l'en-tête de `playwright.config.ts`. Les tests sont isolés (API simulée, aucun état partagé) et joués en parallèle : jamais de variable de module modifiée par un test, jamais de `waitForTimeout`. `make e2e` pour les scénarios contre le vrai back (un test à la fois : un seul compte ; vider le limiteur de débit du back en cas de 429).
5. Test visuel : `make e2e-visual`, **lire les captures** (mobile et bureau, clair et sombre) avant de conclure ; une page visible non vue n'est pas finie.

### 4.2 Nouveau texte ou nouveau code d'erreur
Ajouter la clé dans `fr.ts`, brancher le code dans `driveCodes` de `failures.ts` si c'est un code du back, tester `messageForFailure`.

### 4.3 Changement de format du plan ou du résultat
Ne se fait pas dans le front seul : schémas `drive-agent/protocol/*.schema.json`, validateurs, exemples, `drive-agent/protocol/README.md` et `architecture.md` § 8 du back changent **dans le même commit** (voir `repas-agent-dev`).

### 4.4 Un champ « nom » de recette ou d'ingrédient
Utiliser `<UiTextInput capitalize-first …/>` (ADR 0018) : la première lettre passe en majuscule à la saisie, et le nom envoyé passe par `capitalizeFirst` (`src/design/capitalizeFirst.ts`) dans la mutation, jamais dans le composant seul. Pas sur un champ de recherche, ni sur une unité, un rayon, une liste ou un magasin.

### 4.5 « Copier » une recette d'un autre

Passer par `useCopyRecipeAction` (`src/features/recipes/`) : la copie ne navigue pas, un message confirme, le bouton de la recette passe à « Copiée » (`copiedRecipes`, en mémoire, vidé par `forgetAccountData`). Sur la fiche, le jeu d'actions dépend de la propriété déduite de SES recettes (`mine | other | unknown`) : jamais d'action tant qu'elle est inconnue, « Copier » seul pour un autre, `PlanButton`/Modifier/Supprimer pour soi (ADR 0017, amendement du 2026-10-30).

- [ ] `gh pr checks` : **tous** verts (un contrôle rouge sans rapport avec le changement et reconnu instable se relance : `gh run rerun --failed`, jamais en le masquant), puis `gh pr merge --squash --delete-branch` (autorisé sur ce dépôt), puis `gh issue close <n> -c "Fait par la PR #<m>"`

### Livraison (rappel)

- Une branche depuis `main` à jour par ticket (`feat/drv-4xx-…`), un ticket = une PR = une fusion avant le suivant.
- Jobs de la CI à attendre (`gh pr checks`, boucle `until`, pas de longue attente isolée) : « Qualité et tests », « Bout en bout (Playwright) », « Agent du drive (bout en bout, faux site Leclerc) », « Avis de sécurité (npm audit) », « Docker Lint », « Image Docker (build et fumée) ». Rouge : deux tentatives raisonnables de correction, sinon laisser la PR ouverte et le dire dans le rapport. Ne jamais masquer un test, une règle ESLint ou la couverture.
- Un changement d'API cassant sort d'abord côté back, compatible avec l'ancien front ; le front fige ensuite le contrat sur le commit fusionné du back.

## 6. Erreurs fréquentes

- Écrire un type d'API à la main, ou oublier `make api-update` après un changement du back (la CI rejoue `api-verify`).
- Une clé i18n absente, ou un `console.warn` laissé : le test échoue.
- `localStorage` sans `try/catch`, ou un jeton qui y atterrit.
- Compter sur le seul état en mémoire pour le brouillon de passage : le service worker recharge la page.
- Parler à `window.repasNative` ailleurs que dans `bridge/`, ou supposer l'application Android prête (le pont natif n'y est pas encore : DRV-317, DRV-314).
- Faire du calcul de conditionnements, de tri ou de priorité dans le front (le back valide, le front envoie l'ordre voulu).

## 7. Interdits

Contacter Leclerc ou un autre site d'enseigne ; mettre un identifiant, cookie, jeton, numéro de magasin, ville ou e-mail réels dans le code, un test, une capture ou une PR ; `eval`/`v-html`/`innerHTML` sur une donnée venue de l'agent ou du back ; relâcher la CSP ; baisser le seuil de couverture ; `--no-verify`, force-push, push sur `main` ; fusionner une PR dont un contrôle n'est pas vert ; `make prod` ou déployer sans demande (jusqu'au 2026-10-20 l'approbation de la mise en production était humaine, ADR 0007 du front ; depuis, et jusqu'à la 1.0.0, seul l'assistant principal crée les releases, jamais un sous-agent : voir `CLAUDE.md`).

## Tests : où mettre quoi

Règle complète : ADR 0019 (`docs/adr/0019-pyramide-de-tests.md`).
- **Composant** (Vitest + `@vue/test-utils` + jsdom, `stubApi`, routeur et stores réels) : textes, états, refus du back, enchaînements. C'est le choix par défaut.
- **Unitaire pur** : `// @vitest-environment node` en tête, sans aucun `.vue` importé (même par le routeur).
- **e2e** seulement pour ce que jsdom ne voit pas : mise en page, contraste (axe, les deux thèmes dans la même visite), clavier et focus réels, service worker, `theme-init.js`, pont natif, un parcours nominal. Un test par écran (`e2e/support/screen.ts`), joué sur le téléphone ; `@bureau` / `@bureau-seul` pour le bureau. Captures derrière `E2E_SHOTS`, jamais de `waitForTimeout`.
- Retirer ou descendre un test : lire les deux, contrôle par mutation, tableau de remplacement dans la PR.
- Seuils de couverture en cliquet, `e2e/` type-vérifié. Si le job Playwright dépasse ~4 min, chercher ce qui peut descendre avant de découper en `--shard`.
