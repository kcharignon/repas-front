# CLAUDE.md

Guide pour travailler sur `repas-front`, le front Vue.js de l'application Repas (back : `kcharignon/repas`, Symfony / PHP).
État (2026-10-16) : le front couvre toutes les pages de l'ancien Twig (inventaire de parité : `PARITY.md`) et **est l'interface de production** sur `kantin.eu` ; Twig est supprimé du back (ADR 0018 du dépôt back), qui ne sert plus que l'API.

## Source de vérité

- `docs/adr/` : décisions d'architecture du front (index dans `docs/adr/README.md`). Changer une convention = ADR + ce fichier dans le même commit.
- Contrat de l'API : `docs/api/openapi.json` du dépôt back, figé à un commit précis (`api/contract.json`), types générés dans `src/api/schema.d.ts` ([ADR 0002](docs/adr/0002-sdk-genere-depuis-le-contrat-openapi.md)). Mettre le contrat à jour : `npm run api:update`, relire le diff.
- Plan, inventaire de parité, design, bascule : `docs/front-vuejs-plan.md` du dépôt back.
- **Chantier en cours : envoi de la liste au drive Leclerc** ([ADR 0008](docs/adr/0008-envoi-de-la-liste-au-drive.md), côté back ADR 0022 et 0023 ; agent dans `drive-agent/`, application Android « Repas » dans `android/`, écrans dans `src/features/drive/`, dont `bridge/` : le module `driveBridge` (DRV-402), seul endroit qui connaît le pont natif `window.repasNative` de l'application Repas et le brouillon de passage `repas.drive.run`, double de test `bridge/__tests__/fakeNative.ts` ; écran d'envoi `DriveSendView.vue` avec `buildPlanMessage.ts` (DRV-404), retour `DriveReturnView.vue` : `useDriveReturn.ts` écoute le pont dès `App.vue`, `returnStore.ts` garde le résultat en mémoire après l'avoir recoupé avec le plan envoyé (`restrictToPlan.ts`, DRV-614 : les lignes que le plan n'explique pas sont ignorées, le brouillon de passage garde pour cela les lignes du plan), `choices.ts` en tire les intentions de `PUT /drive/choices` (DRV-405) ; `driveBridge.startSetup()` et `storeReader.ts` font lire le magasin par l'application, `openMenu()` ouvre son menu natif depuis « Mon compte » (DRV-320) ; faux back et faux pont des e2e : `e2e/support/drive.ts`) : lire `docs/drive/README.md` du dépôt back (`kcharignon/repas`) avant de toucher aux listes de courses ou à ce chantier ; les tickets `DRV-3xx` et `DRV-4xx` sont dans `docs/drive/tickets/` de ce dépôt. Règles : jamais de code distant dans l'agent, jamais d'identifiant ni de cookie d'enseigne, jamais de HTML brut de Leclerc dans le dépôt (public). Le front ne parle jamais à Leclerc ni à l'agent : il ne parle qu'au pont natif, par `@/features/drive/bridge` (jamais `window.repasNative` dans un écran) ; l'agent est embarqué dans l'APK et jamais servi par le front ; le plan du drive n'est jamais gardé, et rien du drive n'est lisible hors ligne (ADR 0006 amendé) ; les ADR 0003 et 0006 sont amendés pour dire que le téléphone envoie aussi la liste au drive.

- **Écrans et modules du drive** (`src/features/drive/`, une ligne chacun ; routes `/drive/reglages`, `/drive/envoi/:listId`, `/drive/retour`, `/drive/produits`, `/drive/produits/:slug`, `/drive/aide`) : `DriveSettingsView.vue` réglages (DRV-403), au-dessus de « Votre magasin » la `DrivePrivacyNote.vue` (note de vie privée courte, lien `/drive/aide#vie-privee`) ; `DriveSendView.vue` envoi (DRV-404 ; une ligne par `DriveSendLine.vue`, mode assisté hors de l'application) ; `DriveReturnView.vue` retour et récapitulatif (DRV-405) ; `ProductsView.vue` et `ProductDetailView.vue` « Mes produits » (DRV-410, `choiceDraft.ts`, `choicesQueries.ts`) ; `DriveAccountLinks.vue` et `AppHelpLink.vue` les entrées de « Mon compte » (les premières seulement si `GET /drive/settings` renvoie `enabled: true`, la seconde toujours) ; `DriveHelpView.vue` aide et installation de l'application (DRV-316), qui porte `DrivePrivacyFull.vue` (note complète, ancre `#vie-privee`, DRV-504) ; `DriveEstimate.vue` bloc « Estimation du coût » (DRV-612), formats et rangement dans `estimate.ts`, requête `useDriveEstimate` de `queries.ts` ; `bridge/` le pont natif (voir ci-dessus). **Exemples de contrat du back** : `drive-agent/fixtures/contract/` (copies à l'octet près de `docs/drive/samples/` du back, commit noté dans `SOURCE.md`), mis à jour par `make samples-update ref=<sha>` (`samples-verify`, rejoué par `make quality` et la CI) ; `src/features/drive/__tests__/contract.spec.ts` les confronte au contrat OpenAPI figé, à `buildPlanMessage` + au protocole de l'agent et aux écrans (un champ changé côté back y échoue avec son chemin) ; parcours simulé `e2e/drive-journey.spec.ts` (Pixel 7).

## Stack

Vue 3 (Composition API, `<script setup>`), TypeScript strict, Vite, Vue Router, Pinia, TanStack Query (données serveur), client
OpenAPI généré (`openapi-typescript` + `openapi-fetch`), Tailwind CSS + composants headless (Reka UI), Vitest, Playwright.
**Tout tourne dans Docker** ([ADR 0004](docs/adr/0004-front-dans-docker.md)) : `make up` (http://localhost:5173, branché sur le back de développement), `make check`, `make e2e`. Node 24 (`.nvmrc`) n'est utile que hors Docker.

## Commandes

`make help` les liste toutes (mêmes sections que le back). Les principales :

- `make start` / `stop` / `restart` / `logs` / `status` : le front dans Docker (http://localhost:5173), relais `/api` et `/images` vers le back (`http://php`, réseau `repas_default` : le back de développement doit tourner).
- `make fixtures` : comptes et données de démonstration dans la base du back (`admin@repas.fr` administrateur, `user@repas.fr`, mot de passe `M0t 2 p@sse`), dev seulement, sans rien vider.
- `make check` : lint (oxlint + ESLint), format (Prettier), types (`vue-tsc`), types de l'API, tests. **À passer avant chaque commit.** `make quality` ajoute l'audit et la vérification du contrat.
- `make test-coverage` : seuil dans `vitest.config.ts`, il ne baisse jamais ; `make e2e` : Playwright dans le conteneur contre le vrai back (compte `admin@repas.fr` par défaut, `E2E_EMAIL` / `E2E_PASSWORD` pour un autre) ; `make e2e-visual` : captures, vidéos, rapport sur http://localhost:9323 ; `make lighthouse` : budgets Lighthouse sur l'image de production (`scripts/lighthouse.mjs`) ; `make e2e-offline` : lecture hors-ligne contre l'image de production ([ADR 0006](docs/adr/0006-pwa-et-lecture-hors-ligne.md)). Une vue n'affiche une erreur de lecture que s'il n'y a rien à montrer (`hasFailed`).
- `make agent-build` : construit l'agent du drive (`drive-agent/`, DRV-301) : `drive-agent/dist/agent.js` (un seul fichier IIFE minifié, sans dépendance, embarqué dans l'application Android par DRV-313) et `dist/manifest.json` (`{version, bytes, sha384}`) ; `make agent-verify` construit deux fois et échoue si les empreintes diffèrent (CI, `make quality`) ; `make agent-test` ne joue que les tests de l'agent (`make check` les joue aussi). ESLint interdit dans `drive-agent/src` `eval`, `new Function`, `innerHTML`, un `fetch` vers un autre hôte et tout import non relatif ; budget de 256 000 octets. Structure et règles : `drive-agent/README.md`. `dist/` n'est jamais commité. Le protocole de l'agent (`drive-agent/protocol/`, DRV-302 : schémas JSON, codec, validateurs écrits à la main, exemples) est partagé avec le front par l'alias `@drive-protocol` ; ses tests de conformité (Ajv, dépendance de développement) tournent avec `make agent-test`. L'adaptateur E.Leclerc (`drive-agent/src/leclerc/`, DRV-303 : magasin, recherche, panier, cadence, erreurs) et l'interface superposée (`drive-agent/src/ui/`, DRV-304 : Shadow DOM fermé, textes dans `strings.ts`, page `drive-agent/demo/`, test `e2e/agent-ui.spec.ts` sans back ni serveur) et l'orchestrateur du passage (`drive-agent/src/flow/`, DRV-305 : phase A, reprise par `sessionStorage`, résultat ; DRV-306 : phase B, le choix guidé d'un produit dans une liste affichée par l'agent, `needed` dans le plan ; DRV-307 : mode configuration, lecture du magasin de la page ; DRV-308 : diagnostic, auto-test et rapport copiable sans donnée personnelle, ouvert par la commande `diagnostic` de l'application, ou par `#repas-diagnostic` pour le favori de bureau) sont expliqués dans `drive-agent/README.md`. Un message de l'application qui n'est pas un plan est une *commande* (`{"v":1,"type":"command","command":"diagnostic"}`, DRV-313 : `protocol/command.ts` et `command.schema.json`) ; DRV-318 y ajoute `selftest` (variante de débogage seulement) et le message `selftest-result` de l'agent vers l'application (`protocol/selftest.ts`).
  Toute modification de l'agent (`drive-agent/src`, `drive-agent/protocol`, la chaîne de construction ou `package-lock.json`) change l'empreinte de `agent.js` : `make android-agent-hash` la note dans `android/agent.js.sha384` (à commiter avec le changement ; `make check` échoue sinon, comme la construction de l'APK).
- `make agent-e2e` (alias `make e2e-agent`) : joue l'agent construit dans Chromium (Pixel 7) contre le faux site Leclerc (`drive-agent/fake-leclerc/`, données inventées, local seulement ; `drive-agent/e2e/`, DRV-309), sans back, front ni réseau (~20 s) ; la CI le rejoue (job « Agent du drive (bout en bout) ») ; `make agent-fake` lance ce faux site à la main sur 127.0.0.1:8099 (Node 24 de la machine). Un test échoue si l'agent envoie deux requêtes en parallèle ou plus vite que 800 ms.
- `make lab` : construit le favori de test du chantier drive (`drive-agent/lab/`, outil jetable) dans `drive-agent/lab/dist/lab-bookmarklet.txt` et affiche sa taille (< 60 Ko) ; mode d'emploi pour l'utilisateur : `drive-agent/lab/PROCEDURE.md`.
  Le favori complet est trop gros pour la synchronisation (DRV-006) : `make lab-publish` copie le banc dans `drive-agent/lab/published/lab.js` (servi par jsDelivr une fois fusionné, un test échoue s'il est périmé), puis `make lab-loader sha=<commit de fusion>` écrit `dist/lab-loader.txt`, un chargeur de moins de 1 500 caractères qui tire ce fichier avec son empreinte SHA-384 (DRV-009).
- `make android` : construit l'application Android « Repas Drive » (`android/`, DRV-311) dans Docker (JDK, Gradle, SDK Android) : `android/dist/repas-drive-debug.apk` avec sa taille et son empreinte SHA-256 ; `make android-test` joue les tests Kotlin (application et dérivation de la version) ; `make android-release` produit `android/dist/repas-drive.apk` signé avec une clé fournie par variables d'environnement (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, plus `ANDROID_VERSION_TAG=android-vX.Y.Z` et `ANDROID_VERSION_CODE`) et **refuse sans clé** ; `make android-release-selftest` le prouve avec une clé jetable. Jamais de clé, de mot de passe ni de secret dans le dépôt (public) : seule `android/debug.keystore`, clé de débogage publique, est suivie. Le workflow `android.yml` (séparé de `make check`) joue les tests, l'APK de débogage et l'essai de publication ; structure et règles : `android/README.md`. La coquille Repas (DRV-317, `MainActivity`) charge le front Repas dans une WebView sur `BuildConfig.REPAS_ORIGIN` (`https://kantin.eu/` en publication ; l'APK de débogage vise un autre hôte https par `ANDROID_REPAS_ORIGIN`, et `ANDROID_APK_NAME` nomme son fichier), navigation limitée à cette origine, pont natif `window.repasNative` réservé à elle (`app.info`, `app.menu`, `drive.start`/`drive.setup`/`drive.cancel` puis `drive.result`/`drive.error` : passage du plan et retour, DRV-314, lecture du magasin choisi sur le drive, DRV-320 ; contrat exact dans `android/README.md`), liens `https://kantin.eu/…` entrants avec `autoVerify` (publication de `assetlinks.json` : étape humaine, `android/README.md`) ; le drive est son second écran `DriveActivity` (l'hôte WebView de DRV-312 : mode ordinateur permanent, navigation limitée à `*.leclercdrive.fr`, profil de WebView à part), une seule permission (Internet) ; essais sur téléphone à la main. L'agent (DRV-313) est un actif de l'application : `make android`, `android-test` et `android-release*` le reconstruisent d'abord (`make agent-build`, la CI passe `ANDROID_AGENT=` après l'avoir construit avec Node), la construction échoue si son empreinte n'est pas celle de `android/agent.js.sha384` ; il est injecté par `addDocumentStartJavaScript` dans les seules pages `https://*.leclercdrive.fr`, avec un canal `addWebMessageListener` (`repasHost`, jamais `addJavascriptInterface`). Le menu de l'APK de débogage ajoute « Test automatique (débogage) » (DRV-318 : un geste, un rapport copié et partageable ; commande `selftest` que l'agent n'honore que si le script d'injection de la variante de débogage a annoncé `debug: true` ; `drive-agent/src/selftest/`) et « Plan d'essai (débogage) » ; la pré-version `android-dev-<date>` (workflow `android.yml` lancé à la main, mode d'emploi `android/PROCEDURE.md`) n'est jamais une release de production.
- `make android-lab` : construit l'application Android jetable du chantier drive (`drive-agent/android-lab/`, DRV-011) dans Docker (JDK, Gradle, SDK Android) : tests Kotlin, puis `dist/repas-android-lab.apk` avec sa taille et son empreinte SHA-256 ; `make android-lab-test` ne lance que les tests Kotlin ; `make android-lab-hash` note l'empreinte de `drive-agent/lab/published/lab.js` quand le banc change exprès (l'APK embarque ce fichier et la construction échoue sans cela, `make check` aussi). Le workflow `android-lab.yml` publie l'APK en pré-version `android-lab-<date>` ; mode d'emploi : `drive-agent/android-lab/PROCEDURE.md`.
- `make android-emulator-up` / `android-emulator-down` / `android-emulator-status` : l'émulateur Android de test (DRV-319, `android/emulator/`) dans Docker, sans fenêtre, accéléré par KVM (`/dev/kvm` : `sudo modprobe kvm_intel && sudo chmod 666 /dev/kvm`, ou `/etc/wsl.conf`, étape humaine décrite dans `android/README.md`) ; SDK, image système et AVD dans le volume `android-emulator-sdk`, téléchargés une seule fois. `make android-smoke` construit un APK de débogage qui vise le **faux Repas local** (`repas.test`), démarre l'émulateur au besoin et joue la coquille (page factice qui utilise `repasNative`) puis le drive sur le **faux site local** (rapport et captures dans `android/dist/smoke/`, à lire avant de conclure). `make android-e2e` (DRV-319, partie 2, `android/emulator/e2e.sh`, ~4 min 30 une fois l'émulateur démarré) joue de **vrais passages** : l'agent réel dans la vraie WebView contre le **faux site Leclerc complet** de DRV-309 (`drive-agent/fake-leclerc/`, Node dans le conteneur de l'émulateur, servi en HTTPS sous `courses-test.leclercdrive.fr`) avec le faux Repas qui joue le front : lecture du magasin, passage complet (phase A, phase B, retour dans Repas), « Annuler », abandon, application tuée puis reprise, blocage simulé, site changé ; panier, cadence et requêtes jugés par le faux site ; rapport et captures dans `android/dist/e2e/` (à lire avant de conclure). Le faux certificat n'est accepté que par la WebView de l'émulateur de test, réglée de l'extérieur : l'application ne l'accepte jamais (`android/__tests__/emulator-e2e.spec.ts`). Le DNS de l'émulateur envoie `*.leclercdrive.fr` et `repas.test` vers ces faux sites et ne résout rien d'autre : **jamais le vrai Leclerc**. Cibles manuelles : la CI n'a pas KVM, `make check` n'y touche pas.
- `make samples-update ref=<sha>` / `make samples-verify` : recopier / vérifier les exemples de contrat du back (`drive-agent/fixtures/contract/`, réseau) ; avec un dépôt local du back non fusionné : `npm run samples:update -- <sha> <chemin du dépôt back>` (hors Docker, il lui faut git).
- `make prod` : l'image de production (Caddy) sur http://localhost:8081 ; `make api-update` (`ref=<sha>`) : figer le contrat sur un commit du back et régénérer les types.
- Sans Docker : `npm run check`, `npm run test:e2e`, `npm run audit:prod`.

## Livrer en production

L'infrastructure (serveur, bordure Caddy, `deploy.sh`, sauvegardes) est dans le dépôt back `kcharignon/repas` : skill `/repas-ops` (`/home/kantin/Projet/Repas/.claude/skills/repas-ops/`, recette `references/release.md`), ADR 0017 et 0018 ; ici, [ADR 0007](docs/adr/0007-deploiement-par-release.md). **L'utilisateur n'est pas devops : une étape à la fois, le but expliqué, jamais de secret dans le chat.**

1. PR, CI verte, je fusionne (squash) : seul dépôt où j'ai le droit de fusionner.
2. Quand l'utilisateur veut livrer : `gh release create vX.Y.Z --target main --generate-notes` (`gh release list --limit 3` pour la version suivante ; `--prerelease` pour un essai). Un changement d'API cassant : le back sort d'abord, compatible avec l'ancien front.
3. La CI teste, construit `ghcr.io/kcharignon/repas-front:vX.Y.Z`, puis **le job « Déploiement en production » attend l'utilisateur** : page du run (`gh run list --workflow Release`) → _Review deployments_ → production → _Approve and deploy_. Je ne peux pas approuver ; je donne le lien du run et je surveille (`gh run view <id>`).
4. `deploy.sh front` (serveur) déploie, vérifie que le SPA répond et **revient seul à la version précédente** en cas d'échec. Je vérifie ensuite : `https://kantin.eu/` (200, `<div id="app">`), `/api/v1/health`, et en lecture seule `ssh -i ~/.ssh/repas_deploy deploy@64.227.124.100 'cd /opt/repas && cat state/ok-front && docker compose --profile front ps'`.
5. Mes écritures sur le serveur sont bloquées par le système : un script écrit dans le scratchpad, que l'utilisateur lance avec `! ssh … 'bash -s' < script` (toute commande `docker compose exec -T` y porte `< /dev/null`).

L'image de production ne contient ni nom de domaine ni secret ; ne jamais en ajouter. La politique de contenu (`docker/Caddyfile`) n'autorise aucune image externe : toutes viennent de `/images`, servi par le back.

## Règles

- **Pas de bruit** : un `console.warn` / `console.error` pendant un test fait échouer le test (`src/__tests__/setup.ts`).
- **Design** : composants dans `src/design/` (préfixe `Ui`), jetons dans `src/design/theme.css`, catalogue sur `/design` ([ADR 0003](docs/adr/0003-design-system-basilic-et-safran.md)) ; toute couleur passe par un jeton, jamais un hexadécimal dans un composant.
- **Pas de chaîne en dur** dans un composant : textes dans `vue-i18n` (français seul).
- **Pas de logique métier** dans les composants : elle reste dans le back. Le front affiche, saisit, appelle l'API et relit l'état.
- **Types de l'API générés, jamais écrits à la main** : un changement de contrat doit casser la compilation, pas la production.
- Jeton d'accès **en mémoire uniquement** (jamais `localStorage`) ; refresh par cookie `HttpOnly` (ADR 0015 du back).
- Accessibilité : WCAG AA, cibles tactiles ≥ 44 px, clavier, thème clair et sombre, `prefers-reduced-motion`.
- Un test avant de fusionner ; une page ou un composant visible passe aussi un test visuel dans Chromium (captures lues, mobile et bureau).

## Git et PR

- Commits courts en français au style `feat:` / `fix:` / `chore:` / `docs:` / `test:` / `refactor:`, **sans `Co-Authored-By`**.
- Une branche par unité logique, PR vers `main` avec la description du modèle (Quoi / Vérifié / À relire), **sans pied d'attribution**.
- **Sur ce dépôt, Claude peut créer et fusionner ses PR** (autorisation de l'utilisateur, 2026-10-15), seulement une fois la CI verte,
  en squash. Jamais de push direct sur `main`, jamais de force-push, jamais de `--no-verify`.
- Sur le dépôt back (`kcharignon/repas`) la règle reste l'inverse : Claude ouvre les PR, l'humain les fusionne.
