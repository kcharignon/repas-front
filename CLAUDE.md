# CLAUDE.md

Guide pour travailler sur `repas-front`, le front Vue.js de l'application Repas (back : `kcharignon/repas`, Symfony / PHP).
État (2026-10-16) : le front couvre toutes les pages de l'ancien Twig (inventaire de parité : `PARITY.md`) et **est l'interface de production** sur `kantin.eu` ; Twig est supprimé du back (ADR 0018 du dépôt back), qui ne sert plus que l'API.

## Source de vérité

- `docs/adr/` : décisions d'architecture du front (index dans `docs/adr/README.md`). Changer une convention = ADR + ce fichier dans le même commit.
- Contrat de l'API : `docs/api/openapi.json` du dépôt back, figé à un commit précis (`api/contract.json`), types générés dans `src/api/schema.d.ts` ([ADR 0002](docs/adr/0002-sdk-genere-depuis-le-contrat-openapi.md)). Mettre le contrat à jour : `npm run api:update`, relire le diff.
- Plan, inventaire de parité, design, bascule : `docs/front-vuejs-plan.md` du dépôt back.
- **Chantier en cours : envoi de la liste au drive Leclerc** ([ADR 0008](docs/adr/0008-envoi-de-la-liste-au-drive.md), côté back ADR 0022 et 0023 ; agent dans `drive-agent/`, application Android « Repas » dans `android/`, écrans dans `src/features/drive/`, dont `bridge/` : le module `driveBridge` (DRV-402), seul endroit qui connaît le pont natif `window.repasNative` de l'application Repas et le brouillon de passage `repas.drive.run`, double de test `bridge/__tests__/fakeNative.ts` ; écran d'envoi `DriveSendView.vue` avec `buildPlanMessage.ts` (DRV-404), `appVersion.ts` (DRV-640 : `MIN_DRIVE_APP_VERSION`, la version de l'application sans laquelle l'envoi n'est pas proposé — une phrase « Mets à jour l'application… », un bouton vers `/drive/aide` et les recherches à la main ; version inconnue = trop ancienne ; à relever quand une version de l'application devient nécessaire ; DRV-641 : « Envoyer au drive » de la liste (`ShoppingListHeader.vue`, seul appelant de `POST …/send`, y compris la reprise `?envoyer=` après les réglages) n'existe que dans l'application et lit sa version AVANT de verrouiller la liste, jamais de verrou dans un navigateur ni dans une application trop ancienne), retour `DriveReturnView.vue` : `useDriveReturn.ts` écoute le pont dès `App.vue`, `returnStore.ts` garde le résultat en mémoire après l'avoir recoupé avec le plan envoyé (`restrictToPlan.ts`, DRV-614 : les lignes que le plan n'explique pas sont ignorées, le brouillon de passage garde pour cela les lignes du plan), `choices.ts` en tire les intentions de `PUT /drive/choices` (DRV-405) ; `driveBridge.startSetup()` et `storeReader.ts` font lire le magasin par l'application, `openMenu()` ouvre son menu natif depuis « Moi » (DRV-320) ; faux back et faux pont des e2e : `e2e/support/drive.ts`) : lire `docs/drive/README.md` du dépôt back (`kcharignon/repas`) avant de toucher aux listes de courses ou à ce chantier ; les tickets `DRV-3xx` et `DRV-4xx` sont dans `docs/drive/tickets/` de ce dépôt. Règles : jamais de code distant dans l'agent, jamais d'identifiant ni de cookie d'enseigne, jamais de HTML brut de Leclerc dans le dépôt (public). Le front ne parle jamais à Leclerc ni à l'agent : il ne parle qu'au pont natif, par `@/features/drive/bridge` (jamais `window.repasNative` dans un écran) ; l'agent est embarqué dans l'APK et jamais servi par le front ; le plan du drive n'est jamais gardé, et rien du drive n'est lisible hors ligne (ADR 0006 amendé) ; les ADR 0003 et 0006 sont amendés pour dire que le téléphone envoie aussi la liste au drive. Les outils jetables du spike (banc d'essai du favori `drive-agent/lab/`, application de test `drive-agent/android-lab/`, leurs cibles `make`, leur workflow et leurs pré-versions `android-lab-…`) sont **retirés depuis le 2026-10-19** (revue de sécurité, constat C6) : ils restent dans l'historique Git, ne pas les recréer.
- **Une intention = un clic (2026-10-20, ADR [0008](docs/adr/0008-envoi-de-la-liste-au-drive.md) § 12, agent 0.39.0)** : « Envoyer au drive » et sa fenêtre de confirmation (gardée : elle évite le clic par erreur) sont la seule fois où l'envoi est demandé. L'écran d'envoi (`DriveSendView.vue`) s'ouvre sur `?ouvrir=1` depuis cette confirmation, depuis « Reprendre l'envoi » (liste envoyée et récapitulatif du retour) et depuis le magasin enregistré, et ouvre le drive tout seul dès que le plan et la version de l'application sont lus (« Ouverture du drive… », une seule fois : la demande est retirée de l'adresse aussitôt) ; il garde son écran pour les erreurs, le hors connexion, le hors application, l'application trop ancienne, le drive inutilisable, un autre envoi en cours, une liste sans article. L'agent n'a plus d'écran « Prêt à remplir ton panier » et appuie lui-même sur « Commencer mes courses » (clic natif, repli sur le bandeau si rien ne change en 3 s). Preuves : `e2e/shopping-list-sent.spec.ts`, `e2e/drive-journey.spec.ts` (`trackTaps`) et `drive-agent/e2e/entree.spec.ts` (`trackInteractions`) comptent les gestes de l'utilisateur. Les scénarios de `make android-e2e` / `android-smoke` (`android/emulator/`) attendent encore l'ancien écran « Prêt à remplir ton panier » et le toucher « Commencer » : à réécrire au prochain passage sur l'émulateur.
- **La recherche qui a fait trouver le produit est mémorisée (DRV-650, 2026-10-20, ADR [0008](docs/adr/0008-envoi-de-la-liste-au-drive.md) § 13, agent 0.40.0)** : la ligne `CHOSEN` du résultat porte la clé facultative `searchQuery` (produit `PRIMARY`, recherche différente de celle du plan) ; `cleanSearchQuery` (`drive-agent/protocol/clean-text.ts`, 2 à 80 points de code, sans `Cc`/`Cf`/`Zl`/`Zp`) la nettoie dans l'agent **et** dans le site (`src/features/drive/choices.ts`, jamais `null`, jamais sur autre chose qu'`ADD_PRODUCT`), car le back refuse tout le lot sur une seule recherche mal formée. - **Équation d'une conversion** (`src/features/ingredients/ConversionEquation.vue`, `equationMath.ts` pur ; l'administration des conversions, la fiche d'un ingrédient dont les deux unités diffèrent et les feuilles de conversions propres) : on écrit `[nombre] [unité] = [nombre] [unité]`, la phrase se lit en direct (`aria-live`), les noms s'accordent avec les nombres (`unitLabel` : « cuillères à soupe »), les erreurs (nombre ≤ 0, mêmes unités) tout de suite. Le coefficient du back est `coefficientOf(gauche, droite)` = droite ÷ gauche. **Deux voix.** Sans `ingredientName` (administration) : « 1 tasse = 0,125 kilo, et 1 kilo = 8 tasses. ». Avec `ingredientName` (un ingrédient, même vide à la création) : la question « Dans 1 bouteille, combien de centilitres ? » (noms réels des unités, `withDe` élide « de ») et UNE phrase dans le sens écrit (« Vin : 1 bouteille = 30 centilitres. »), jamais la réciproque (la question complexe à répondre). **Sens voulu pour tout ce qui touche UN ingrédient : `1 [unité d'achat] = N [unité de recette]`** (« 1 bouteille = 30 centilitres », jamais « 1 centilitre = 0,0333 bouteille » ; Twig faisait ainsi), à la création, à la réouverture, dans la fiche, dans « Régler » et dans « Conversions de {nom} », quel que soit le sens ou la valeur enregistrés (elle peut valoir moins de 1 : « 1 kilo = 0,5 sac »). `displayOrientation(conversion, unitéAchat)` (pur) dit comment lire une conversion enregistrée : l'unité d'achat passe à gauche si elle y est, sinon on retourne ce qui vaut moins de 1 ; retourner n'écrit rien (une équation intacte ne renvoie rien : fiche `coefficient: null`, feuille de modification fermée sans `PUT`, la conversion enregistrée à l'envers ne bouge pas et ne reçoit pas de doublon). La fiche retrouve la conversion de la paire achat/recettes par `GET /api/v1/ingredients/{slug}/conversions` (`member` puis `common`, dans un sens ou l'autre ; la fiche seule ne rend `coefficient` que pour « achat vers recettes ») ; sans conversion directe mais avec `convertible`, le nombre reste vide et la phrase dit « Elles se convertissent déjà ; tu peux préciser. ». Les deux unités de la fiche sont celles du formulaire, écrites et non choisies ; dans les feuilles elles se choisissent et s'inversent, et le focus va au nombre de droite (`focusRight`, après le piège à focus de la feuille). Pas de calcul de métier ailleurs que dans `equationMath.ts`. e2e : `e2e/conversion-equation.spec.ts` (faux back local, axe, clair et sombre, dont « 1 bouteille = 30 centilitres » enregistrée dans les deux sens puis rouverte).
- **Conversions propres à un ingrédient et lignes de recette à régler (2026-10-27, back `#299`, `docs/ingredients/`)** : `GET /api/v1/recipes/{id}` dit pour chaque ligne si l'unité se convertit dans l'unité d'achat de son ingrédient (`convertible`, `purchaseUnitName`). `RecipeDetailView.vue` repère la ligne qui ne se convertit pas (`convertible === false`, jamais quand le champ manque : un ancien back ne signale rien), **seulement pour l'auteur de la recette** (`isMine`) : une ligne ambre sous le nom (« Je ne sais pas convertir en kilo » + « Régler »), une pastille « N à régler » près du titre qui mène à la première, « Ajouter » grisé avec son texte (`PlanButton` `blocked`, une recette déjà dans la liste se retire toujours). Les refus du back ont leur phrase (`conversionCodes` de `failures.ts` : `CONVERSION_ALREADY_EXISTS`, `CONVERSION_REQUIRED_BY_INGREDIENT`, `CONVERSION_SAME_UNIT`). ## Livrer en production

L'infrastructure (serveur, bordure Caddy, `deploy.sh`, sauvegardes) est dans le dépôt back `kcharignon/repas` : skill `/repas-ops` (`/home/kantin/Projet/Repas/.claude/skills/repas-ops/`, recette `references/release.md`), ADR 0017 et 0018 ; ici, [ADR 0007](docs/adr/0007-deploiement-par-release.md). **L'utilisateur n'est pas devops : une étape à la fois, le but expliqué, jamais de secret dans le chat.**

1. PR, CI verte, je fusionne (squash) : j'ai le droit de fusionner sur ce dépôt comme sur le back.
2. Quand l'utilisateur veut livrer : `gh release create vX.Y.Z --target main --generate-notes` (`gh release list --limit 3` pour la version suivante ; `--prerelease` pour un essai). Un changement d'API cassant : le back sort d'abord, compatible avec l'ancien front.
   **Mise à jour du 2026-10-24 : fin de la phase bêta, la prochaine version déployée est la 1.0.0 et l'approbation du déploiement est revenue, pour le site comme pour le back** (décision de l'utilisateur, ADR 0017 du back, amendement du 2026-10-24). L'environnement GitHub `production` a de nouveau un relecteur obligatoire ; c'est l'assistant principal (pas un sous-agent) qui crée les releases (`vX.Y.Z` du site et du back) et qui suit le run. Garde-fous : tests et contrôles verts avant l'image ; sauvegarde et retour arrière automatiques de `deploy/deploy.sh` (dépôt back) ; une seule release du site à la fois (attendre que la précédente soit déployée) ; ordre back, site, puis application quand un changement d'API ou de protocole l'exige. Inchangé : les sous-agents de code ne créent ni tag ni release et ne déploient pas ; l'allumage de `DRIVE_ENABLED` reste à l'humain. Entre le 2026-10-20 et le 2026-10-24 (bêta), le déploiement partait sans approbation.
3. La CI teste, construit `ghcr.io/kcharignon/repas-front:vX.Y.Z`, puis **le job « Déploiement en production » attend l'utilisateur** : page du run (`gh run list --workflow Release`) → _Review deployments_ → production → _Approve and deploy_. Je ne peux pas approuver (mon jeton n'a pas « Deployments ») et je n'approuverais pas : je le préviens avec le lien du run dès que le job est `waiting`, et je surveille le run (`gh run view <id>`).

Je vérifie ensuite : `https://kantin.eu/` (200, `<div id="app">`), `/api/v1/health`, et en lecture seule `ssh -i ~/.ssh/repas_deploy deploy@64.227.124.100 'cd /opt/repas && cat state/ok-front && docker compose --profile front ps'`.

## Règles

- **Pas de bruit** : un `console.warn` / `console.error` pendant un test fait échouer le test (`src/__tests__/setup.ts`).
- **Design** : composants dans `src/design/` (préfixe `Ui`), jetons dans `src/design/theme.css`, catalogue sur `/design` ([ADR 0003](docs/adr/0003-design-system-basilic-et-safran.md)) ; toute couleur passe par un jeton, jamais un hexadécimal dans un composant.
- **Pas de chaîne en dur** dans un composant : textes dans `vue-i18n` (français seul).
- **Pas de logique métier** dans les composants : elle reste dans le back. Le front affiche, saisit, appelle l'API et relit l'état.
- **Types de l'API générés, jamais écrits à la main** : un changement de contrat doit casser la compilation, pas la production.
- Jeton d'accès **en mémoire uniquement** (jamais `localStorage`) ; refresh par cookie `HttpOnly` (ADR 0015 du back).
- Accessibilité : WCAG AA, cibles tactiles ≥ 44 px, clavier, thème clair et sombre, `prefers-reduced-motion`.
- Un test avant de fusionner ; une page ou un composant visible passe aussi un test visuel dans Chromium (captures lues, mobile et bureau).
