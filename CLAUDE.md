# CLAUDE.md

Guide pour travailler sur `repas-front`, le front Vue.js de l'application Repas (back : `kcharignon/repas`, Symfony / PHP).
État (2026-10-16) : le front couvre toutes les pages de l'ancien Twig (inventaire de parité : `PARITY.md`) et **est l'interface de production** sur `kantin.eu` ; Twig est supprimé du back (ADR 0018 du dépôt back), qui ne sert plus que l'API.

## Source de vérité

- `docs/adr/` : décisions d'architecture du front (index dans `docs/adr/README.md`). Changer une convention = ADR + ce fichier dans le même commit.
- Contrat de l'API : `docs/api/openapi.json` du dépôt back, figé à un commit précis (`api/contract.json`), types générés dans `src/api/schema.d.ts` ([ADR 0002](docs/adr/0002-sdk-genere-depuis-le-contrat-openapi.md)). Mettre le contrat à jour : `npm run api:update`, relire le diff.
- Plan, inventaire de parité, design, bascule : `docs/front-vuejs-plan.md` du dépôt back.
- **Chantier en cours : envoi de la liste au drive Leclerc** ([ADR 0008](docs/adr/0008-envoi-de-la-liste-au-drive.md), côté back ADR 0022 et 0023 ; agent dans `drive-agent/`, application Android « Repas » dans `android/`, écrans dans `src/features/drive/`, dont `bridge/` : le module `driveBridge` (DRV-402), seul endroit qui connaît le pont natif `window.repasNative` de l'application Repas et le brouillon de passage `repas.drive.run`, double de test `bridge/__tests__/fakeNative.ts` ; écran d'envoi `DriveSendView.vue` avec `buildPlanMessage.ts` (DRV-404), `appVersion.ts` (DRV-640 : `MIN_DRIVE_APP_VERSION`, la version de l'application sans laquelle l'envoi n'est pas proposé — une phrase « Mets à jour l'application… », un bouton vers `/drive/aide` et les recherches à la main ; version inconnue = trop ancienne ; à relever quand une version de l'application devient nécessaire ; DRV-641 : « Envoyer au drive » de la liste (`ShoppingListHeader.vue`, seul appelant de `POST …/send`, y compris la reprise `?envoyer=` après les réglages) n'existe que dans l'application et lit sa version AVANT de verrouiller la liste, jamais de verrou dans un navigateur ni dans une application trop ancienne), retour `DriveReturnView.vue` : `useDriveReturn.ts` écoute le pont dès `App.vue`, `returnStore.ts` garde le résultat en mémoire après l'avoir recoupé avec le plan envoyé (`restrictToPlan.ts`, DRV-614 : les lignes que le plan n'explique pas sont ignorées, le brouillon de passage garde pour cela les lignes du plan), `choices.ts` en tire les intentions de `PUT /drive/choices` (DRV-405) ; `driveBridge.startSetup()` et `storeReader.ts` font lire le magasin par l'application, `openMenu()` ouvre son menu natif depuis « Moi » (DRV-320) ; faux back et faux pont des e2e : `e2e/support/drive.ts`) : lire `docs/drive/README.md` du dépôt back (`kcharignon/repas`) avant de toucher aux listes de courses ou à ce chantier ; les tickets `DRV-3xx` et `DRV-4xx` sont dans `docs/drive/tickets/` de ce dépôt. Règles : jamais de code distant dans l'agent, jamais d'identifiant ni de cookie d'enseigne, jamais de HTML brut de Leclerc dans le dépôt (public). Le front ne parle jamais à Leclerc ni à l'agent : il ne parle qu'au pont natif, par `@/features/drive/bridge` (jamais `window.repasNative` dans un écran) ; l'agent est embarqué dans l'APK et jamais servi par le front ; le plan du drive n'est jamais gardé, et rien du drive n'est lisible hors ligne (ADR 0006 amendé) ; les ADR 0003 et 0006 sont amendés pour dire que le téléphone envoie aussi la liste au drive. Les outils jetables du spike (banc d'essai du favori `drive-agent/lab/`, application de test `drive-agent/android-lab/`, leurs cibles `make`, leur workflow et leurs pré-versions `android-lab-…`) sont **retirés depuis le 2026-10-19** (revue de sécurité, constat C6) : ils restent dans l'historique Git, ne pas les recréer.

## Stack

Vue 3 (Composition API, `<script setup>`), TypeScript strict, Vite, Vue Router, Pinia, TanStack Query (données serveur), client
OpenAPI généré (`openapi-typescript` + `openapi-fetch`), Tailwind CSS + composants headless (Reka UI), Vitest, Playwright.
**Tout tourne dans Docker** ([ADR 0004](docs/adr/0004-front-dans-docker.md)) : `make up` (http://localhost:5173, branché sur le back de développement), `make check`, `make e2e`. Node 24 (`.nvmrc`) n'est utile que hors Docker.

## Commandes

`make help` les liste toutes (mêmes sections que le back). Les principales :

- `make start` / `stop` / `restart` / `logs` / `status` : le front dans Docker (http://localhost:5173), relais `/api` et `/images` vers le back (`http://php`, réseau `repas_default` : le back de développement doit tourner).
- `make fixtures` : comptes et données de démonstration dans la base du back (`admin@repas.fr` administrateur, `user@repas.fr`, mot de passe `M0t 2 p@sse`), dev seulement, sans rien vider.
- `make check` : lint (oxlint + ESLint), format (Prettier), types (`vue-tsc`), types de l'API, tests. **À passer avant chaque commit.** `make quality` ajoute l'audit et la vérification du contrat.
- `make test-coverage` : seuil dans `vitest.config.ts`, il ne baisse jamais ; `make e2e` : Playwright dans le conteneur contre le vrai back (compte `admin@repas.fr` par défaut, `E2E_EMAIL` / `E2E_PASSWORD` pour un autre) ; `make e2e-visual` : captures, vidéos, rapport sur http://localhost:9323 ; `make lighthouse` : budgets Lighthouse sur l'image de production (`scripts/lighthouse.mjs`) ; `make e2e-offline` : lecture hors-ligne contre l'image de production ([ADR 0006](docs/adr/0006-pwa-et-lecture-hors-ligne.md)). Une vue n'affiche une erreur de lecture que s'il n'y a rien à montrer (`hasFailed`).
- `make agent-build` : construit l'agent du drive (`drive-agent/`, DRV-301) : `drive-agent/dist/agent.js` (un seul fichier IIFE minifié, sans dépendance, embarqué dans l'application Android par DRV-313) et `dist/manifest.json` (`{version, bytes, sha384}`) ; `make agent-verify` construit deux fois et échoue si les empreintes diffèrent (CI, `make quality`) ; `make agent-test` ne joue que les tests de l'agent (`make check` les joue aussi). ESLint interdit dans `drive-agent/src` `eval`, `new Function`, `innerHTML`, un `fetch` vers un autre hôte et tout import non relatif ; budget de 256 000 octets. Structure et règles : `drive-agent/README.md`. `dist/` n'est jamais commité. Le protocole de l'agent (`drive-agent/protocol/`, DRV-302 : schémas JSON, codec, validateurs écrits à la main, exemples) est partagé avec le front par l'alias `@drive-protocol` ; ses tests de conformité (Ajv, dépendance de développement) tournent avec `make agent-test`. L'adaptateur E.Leclerc (`drive-agent/src/leclerc/`, DRV-303 : magasin, recherche, panier, cadence, erreurs) et l'interface superposée (`drive-agent/src/ui/`, DRV-304 : Shadow DOM fermé, **photos des produits** dans l'écran de choix et la question « Toujours prendre ce produit ? » (DRV-633 : `photo-url.ts` valide l'adresse lue, `https` d'un hôte `leclercdrive.fr` ou sous-domaine, ni identifiant ni port, 2 000 caractères ; `ui/photo.ts` bâtit la balise `img` par le DOM ; une par fiche affichée, chargement différé, retirée sans trace si elle ne charge pas, jamais envoyée à Repas ni gardée), **tous les résultats de la recherche, affichés par lots en défilant (DRV-643 : 200 au plus, huit fiches puis la suite quand la sentinelle approche, aucune requête de plus au site, une seule page de résultats lue, pas de pagination)**, **un produit que le panier ne prend pas est quand même enregistré (DRV-644 : ligne `CHOSEN` ordinaire, le passage continue, la fin dit en une phrase pourquoi, `UnreachedReason` : `COMING_SOON`, `OUT_OF_STOCK`, `CART_REFUSED`, un état de l'agent sans clé de plus dans le résultat)**, textes dans `strings.ts`, **échelle d'affichage** `scale.ts` : l'interface s'agrandit de 1 / `visualViewport.scale` (facteur 2,38 sur un Pixel 9 où le site s'affiche en mode ordinateur, 1 ailleurs) pour rester lisible et touchable (48 px, `drive-agent/e2e/affichage.spec.ts`), page `drive-agent/demo/`, test `e2e/agent-ui.spec.ts` sans back ni serveur) et l'orchestrateur du passage (`drive-agent/src/flow/`, DRV-305 : phase A, reprise par `sessionStorage`, résultat ; DRV-306 : phase B, le choix guidé d'un produit dans une liste affichée par l'agent, `needed` dans le plan ; DRV-307 : mode configuration, lecture du magasin de la page ; DRV-308 : diagnostic, auto-test et rapport copiable sans donnée personnelle (ticket B de l'audit : sondes du site réel, formes, noms et nombres seulement, `diagnostic-probes.spec.ts` ; la recherche se fait sur le chemin avec ville tiré de la page, avec repli sur HTTP 400, `search-request.ts`), ouvert par la commande `diagnostic` de l'application, ou par `#repas-diagnostic` pour le favori de bureau) sont expliqués dans `drive-agent/README.md`. Durcissement face au vrai site (audit du 2026-10-18) : toute erreur de l'adaptateur porte une **cause** (`LeclercError.cause`, `drive-agent/src/leclerc/causes.ts` : « Le site a changé (SEARCH_NO_STATE) » dans `error.message` du résultat et dans le diagnostic) ; une recherche sans produit mais au squelette du magasin est une liste vide, pas une panne (`search-page.ts`) ; la page d'un visiteur non connecté arrête l'envoi avant toute écriture (`session.ts`, signes cumulés non mesurés). **Chercher dans le bon rayon (DRV-642, agent 0.31.0)** : le plan peut porter, par ligne, `rayonHints` (0 à 3 identifiants de rayon de l'enseigne, du plus choisi au moins choisi, facultatif) ; l'agent range alors la liste de l'écran de choix (phase B et « Chercher autre chose ») avec les produits de ces rayons d'abord, **sans en cacher aucun** (`leclerc/aisle.ts`, `rankByAisle`, avant le plafond et l'affichage par lots), et le produit choisi renvoie `rayonId` et `familyId` (facultatifs, `iIdRayon` / `iIdFamille`) que le front recopie dans `PUT /drive/choices` (`choices.ts`) ; aucun texte visible nouveau. Le web n'envoie `rayonHints` qu'à une application dont l'agent les connaît (`RAYON_HINTS_APP_VERSION`, `appVersion.ts` : un agent ancien rejette un plan qui porte une clé inconnue) ; types de ces champs générés dans `src/api/schema.d.ts` (`rayonHintsOf` dans `buildPlanMessage.ts`, `catalogIdOf` dans `choices.ts`). **Libellés de rayons, mesure (DRV-647 étape 0, agent 0.32.0)** : le diagnostic dit, sans requête de plus, la structure de la réponse de recherche (noms de clés seulement, `leclerc/reply-shape.ts`), les liens du menu « Rayons » de la page lus dans le DOM sans clic (numéro et libellé de catalogue, 40 au plus, `leclerc/aisle-menu.ts`) et combien des rayons de « tomate » y ont un lien ; détail dans `drive-agent/README.md`. Quand la recherche d'un nom ne rend aucun produit, l'agent essaie ses formes dérivées une par une (ticket D : `flow/search-forms.ts` et `search-by-name.ts`, au plus 4 requêtes de repli par nom, à la cadence normale, jamais deux fois la même ; seulement la recherche faite par l'agent, jamais ce que l'utilisateur tape ; faux site : `strictSearch`). **Introuvable n'est pas indisponible, le panier tranche (DRV-635)** : un produit habituel se cherche par son libellé tel quel puis par `productSearchForms` (jamais un signe remplacé par une espace : « c est » ne trouve rien sur le vrai site, « c'est » et « cest » oui ; 5 requêtes au plus) ; stock nul et « Bientôt disponible » sont des étiquettes, le produit est tenté une fois et le panier tranche ; trois raisons (`OUT_OF_STOCK`, `NOT_FOUND`, `CART_REFUSED`, un état de l'agent : aucune clé nouvelle dans le résultat), dites dans l'écran, le journal, « Détails » et le diagnostic ; faux site : `strictApostrophe`, `availability`. Un message de l'application qui n'est pas un plan est une _commande_ (`{"v":1,"type":"command","command":"diagnostic"}`, DRV-313 : `protocol/command.ts` et `command.schema.json`) ; DRV-318 y ajoute `selftest` (variante de débogage seulement) et le message `selftest-result` de l'agent vers l'application (`protocol/selftest.ts`).
  Toute modification de l'agent (`drive-agent/src`, `drive-agent/protocol`, la chaîne de construction ou `package-lock.json`) change l'empreinte de `agent.js` : `make android-agent-hash` la note dans `android/agent.js.sha384` (à commiter avec le changement ; `make check` échoue sinon, comme la construction de l'APK).
- `make agent-e2e` (alias `make e2e-agent`) : joue l'agent construit dans Chromium (Pixel 7) contre le faux site Leclerc (`drive-agent/fake-leclerc/`, données inventées, local seulement ; `drive-agent/e2e/`, DRV-309), sans back, front ni réseau (~20 s) ; la CI le rejoue (job « Agent du drive (bout en bout) ») ; `make agent-fake` lance ce faux site à la main sur 127.0.0.1:8099 (Node 24 de la machine). Un test échoue si l'agent envoie deux requêtes en parallèle ou plus vite que 800 ms.
- `make android` : construit l'application Android « Repas Drive » (`android/`, DRV-311) dans Docker (JDK, Gradle, SDK Android) : `android/dist/repas-drive-debug.apk` avec sa taille et son empreinte SHA-256 ; `make android-test` joue les tests Kotlin (cœur, application et dérivation de la version) ; `make android-release` produit `android/dist/repas-drive.apk` signé avec une clé fournie par variables d'environnement (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, plus `ANDROID_VERSION_TAG=android-vX.Y.Z`, dont le code de version est tiré : `X * 1 000 000 + Y * 1 000 + Z`) et **refuse sans clé** ; `make android-release-verify` contrôle cet APK (`ANDROID_EXPECTED_CERT_SHA256` : certificat attendu et jamais la clé de débogage, version de l'étiquette, une seule permission, non débogable, agent intact) ; `make android-release-selftest` prouve le refus sans clé, la réussite avec une clé jetable et les refus du contrôle. Jamais de clé, de mot de passe ni de secret dans le dépôt (public) : seule `android/debug.keystore`, clé de débogage publique, est suivie. Le workflow `android.yml` (séparé de `make check`) joue les tests, l'APK de débogage et l'essai de publication ; structure et règles : `android/README.md`. **Publication signée (DRV-315)** : `android-release.yml` se déclenche **uniquement** sur le push d'une étiquette `android-vX.Y.Z` par l'utilisateur (jamais sur une PR ni sur `main`), lit les quatre secrets GitHub (mêmes noms que les variables ci-dessus, dans un travail en lecture seule) puis publie, dans un second travail sans secret, une release ordinaire (`repas-drive.apk`, `.sha256`, `version.json`, notes avec SHA-256, version de l'agent et empreinte du certificat) après contrôle de l'APK ; le certificat attendu est celui de `public/.well-known/assetlinks.json` (à publier avant la première version) ; **procédure humaine pas à pas : `android/PUBLICATION.md`** (clé, secrets, `assetlinks.json`, étiquette, installation, mise à jour). Claude ne crée jamais l'étiquette, ne touche jamais aux secrets ni à la clé ; la pré-version `android-dev-…` est signée d'une clé de débogage publique et ne s'installe jamais sur le téléphone des courses (avertissement dans ses notes ; les anciennes `android-lab-…` du banc d'essai retiré sont à supprimer de la page des releases). La coquille Repas (DRV-317, `MainActivity`) charge le front Repas dans une WebView sur `BuildConfig.REPAS_ORIGIN` (`https://kantin.eu/` en publication ; l'APK de débogage vise un autre hôte https par `ANDROID_REPAS_ORIGIN`, et `ANDROID_APK_NAME` nomme son fichier), navigation limitée à cette origine, pont natif `window.repasNative` réservé à elle (`app.info`, `app.menu`, `drive.start`/`drive.setup`/`drive.cancel` puis `drive.result`/`drive.error` : passage du plan et retour, DRV-314, lecture du magasin choisi sur le drive, DRV-320 ; contrat exact dans `android/README.md`), liens `https://kantin.eu/…` entrants avec `autoVerify` (publication de `assetlinks.json` : étape humaine, `android/README.md`) ; le drive est son second écran `DriveActivity` (l'hôte WebView de DRV-312 : mode ordinateur permanent, navigation limitée à `*.leclercdrive.fr`, profil de WebView à part), une seule permission (Internet) ; essais sur téléphone à la main. ## Livrer en production

L'infrastructure (serveur, bordure Caddy, `deploy.sh`, sauvegardes) est dans le dépôt back `kcharignon/repas` : skill `/repas-ops` (`/home/kantin/Projet/Repas/.claude/skills/repas-ops/`, recette `references/release.md`), ADR 0017 et 0018 ; ici, [ADR 0007](docs/adr/0007-deploiement-par-release.md). **L'utilisateur n'est pas devops : une étape à la fois, le but expliqué, jamais de secret dans le chat.**

1. PR, CI verte, je fusionne (squash) : j'ai le droit de fusionner sur ce dépôt comme sur le back.
2. Quand l'utilisateur veut livrer : `gh release create vX.Y.Z --target main --generate-notes` (`gh release list --limit 3` pour la version suivante ; `--prerelease` pour un essai). Un changement d'API cassant : le back sort d'abord, compatible avec l'ancien front.
3. La CI teste, construit `ghcr.io/kcharignon/repas-front:vX.Y.Z`, puis **le job « Déploiement en production » attend l'utilisateur** : page du run (`gh run list --workflow Release`) → _Review deployments_ → production → _Approve and deploy_. Je ne peux pas approuver ; je donne le lien du run et je surveille (`gh run view <id>`).
4. `deploy.sh front` (serveur) déploie, vérifie que le SPA répond et **revient seul à la version précédente** en cas d'échec. Je vérifie ensuite : `https://kantin.eu/` (200, `<div id="app">`), `/api/v1/health`, et en lecture seule `ssh -i ~/.ssh/repas_deploy deploy@64.227.124.100 'cd /opt/repas && cat state/ok-front && docker compose --profile front ps'`.
5. Mes écritures sur le serveur sont bloquées par le système : un script écrit dans le scratchpad, que l'utilisateur lance avec `! ssh … 'bash -s' < script` (toute commande `docker compose exec -T` y porte `< /dev/null`).

**L'application Android se livre à part** : l'APK signé se publie par une étiquette `android-vX.Y.Z` que **l'utilisateur** pousse (`git push origin android-v0.1.0`, `android-release.yml`), jamais par `gh release create` ni par `release.yml` ; pas à pas : `android/PUBLICATION.md` (clé de signature, quatre secrets, `assetlinks.json` à publier avec le site avant la première version).

L'image de production ne contient ni nom de domaine ni secret ; ne jamais en ajouter. La politique de contenu (`docker/Caddyfile`) n'autorise aucune image externe : toutes viennent de `/images`, servi par le back.

## Règles

- **Pas de bruit** : un `console.warn` / `console.error` pendant un test fait échouer le test (`src/__tests__/setup.ts`).
- **Design** : composants dans `src/design/` (préfixe `Ui`), jetons dans `src/design/theme.css`, catalogue sur `/design` ([ADR 0003](docs/adr/0003-design-system-basilic-et-safran.md)) ; toute couleur passe par un jeton, jamais un hexadécimal dans un composant.
- **Pas de chaîne en dur** dans un composant : textes dans `vue-i18n` (français seul).
- **Pas de logique métier** dans les composants : elle reste dans le back. Le front affiche, saisit, appelle l'API et relit l'état.
- **Types de l'API générés, jamais écrits à la main** : un changement de contrat doit casser la compilation, pas la production.
- Jeton d'accès **en mémoire uniquement** (jamais `localStorage`) ; refresh par cookie `HttpOnly` (ADR 0015 du back).
- Accessibilité : WCAG AA, cibles tactiles ≥ 44 px, clavier, thème clair et sombre, `prefers-reduced-motion`.
- Un test avant de fusionner ; une page ou un composant visible passe aussi un test visuel dans Chromium (captures lues, mobile et bureau).
